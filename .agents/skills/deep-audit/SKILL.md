# 全仓审计

## 与 deep-review 的分工

| | deep-review | deep-audit(本 skill) | deep-test |
|---|---|---|---|
| 入口 | 当前改动 | 整个仓库 | 指定范围的现有测试与门禁 |
| 产出 | 现在就该修的缺陷 | 需要排期的评估结论 | 失效测试清单 + 补上的门禁 |
| 终点 | 修完过 CI | 分级报告 + 处理顺序 | 变异全部能抓住 + 门禁复跑 |
| 频率 | 每次提交前 | 上线前 / 里程碑 / 季度 | 新模块完成时 / 门禁可信度存疑时 |

审计**默认不进入修复**。用户挑中某几条之后,那几条走 `deep-review` 的修复流程(按类修 + 不变量测试 + 变异验证 + CI)。

证据门槛、归类扫类、不变量测试、变异验证、CI 探测,读 `../deep-review/references/method.md`。审计同样适用 —— **一条没有证据的架构判断就是一句意见**。

## 两条纪律(比找到问题更重要)

**一、"不动"是合法且常见的结论。** 审计最大的失败模式是把一个能跑、有测试、团队熟悉的系统判成"需要重构"。任何结构性改动建议必须写明:它解决的**具体问题是什么**、这个问题**已经造成了什么**、以及不改的代价。写不出来就不要建议。

**二、设计原则和设计模式是诊断词汇,不是评分表。** 不要逐条给 SOLID 打分,也不要清点用了几种模式。正确用法是反过来:先找到一个**具体的坏现象**(改一处要动五个文件、加一个类型要改 switch、测试必须起数据库),再用原则的名字说清它为什么发生。没有坏现象就没有结论。

## 调用

```
/deep-audit           全仓审计
/deep-audit <路径>    限定到某个子树(大仓库建议这样切分)
```

## 流程

### 阶段 1 — 建地图(先别评价)

不要一上来就读代码文件。先建立结构认知:

- 模块/包清单与各自职责(README、目录名、包注释)
- 依赖方向图:谁依赖谁,有没有环,有没有反向依赖
- 入口点:main、路由注册、实际生成的 Swagger/OpenAPI、定时任务、消息消费者
- 构建与 CI:实际跑什么(见 method.md 的 CI 探测)
- 规模分布:哪些文件/包异常大,哪些几乎是空的
- 测试分布:哪些模块有测试,覆盖率如何(如果 CI 会算)

用 `git log` 补一层动态信息:**改动最频繁的文件**、**最近半年没人碰过的模块**。前者是耦合与设计压力的指示器,后者是停滞或已死代码的指示器。

这一阶段只产出事实,不下判断。

### 阶段 2 — 有纪律的采样

全仓不可能逐行读。按"最可能出问题"采样,并在报告里**写明采了什么、没采什么**:

- 改动最频繁的前若干文件(设计压力集中处)
- 最大的几个文件/函数(复杂度集中处)
- 跨模块边界的代码(耦合发生处)
- 所有入口点(契约与鉴权发生处)
- 全量生成的 Swagger/OpenAPI operation 与运行时路由映射(结构化规范不做抽样)
- 没有测试的模块(风险集中处)
- 依赖清单全量(这个可以真的全看)

### 阶段 3 — 并行视角

读 `../deep-review/references/perspectives.md`,派 subagent。审计侧重这几个视角,每个给定采样范围:

- **架构与耦合** —— 依赖方向、循环、单实现抽象、平行的第二套模式、模块自治度
- **复用与重复** —— 跨模块的重复实现、可提取的公共能力
- **依赖健康** —— 全量清单:版本落后多少、上游是否停维护、许可证、传递污染、能否移除
- **命名与注释一致性** —— 目录/文件/结构体/字段的用词是否语义明确、是否与内容相符、注释是否还成立
- **安全与越权** —— 按接口逐个核对四类越权,重点查旁路(导出、下拉数据源、附件下载)
- **存量数据与版本兼容** —— 已上线系统必看:旧规则创建的数据在新代码下的读改删导出
- **数值与精度** —— 有金额/计费/分摊的系统必看:存储类型、舍入方向、余数归属
- **性能 / 事务与分布式 / 跨平台** —— 按采样范围
- **产品闭环** —— 从入口点出发,每条用户可见路径能进能出、有失败有恢复
- **Swagger/OpenAPI 接口规范** —— 路径与资源层级、参数位置和命名、HTTP 语义、operationId/tag/security、schema/错误响应及跨接口一致性

审计特有的一个视角:

**规范符合性** —— 语言官方风格与惯用法(Effective Go、PEP 8 等)、Conventional Commits、SemVer、12-factor、REST/OpenAPI 约定、错误处理惯例、日志与配置约定。**只报"偏离且造成了实际问题"的**,不报"和某本书不一样"。

同样的规则:**视角交白卷是完整答案**,不要凑。

派完视角后再做一次反向核对:按 `../deep-review/references/failure-patterns.md` 的 A 类八条,
对每个主要模块判定是否触及、是否已有对应防护与验证。**判定为不触及也要写理由。**
这一步产出的是"整条路径可能整体失效"的结论,与逐视角的采样互补 —— 审计报告里单列一节。

### Swagger/OpenAPI 接口审计

仓库或审计子树只要提供 HTTP API，就必须读 `../deep-review/references/openapi.md`，生成或取得部署实际使用的
Swagger/OpenAPI，而不是只看 handler、注解或手写规范。对规范中的 operation 做全量结构化检查，并与运行时路由、
鉴权和校验行为抽样对照；报告路径风格、参数、HTTP 方法/状态码、分页过滤排序、错误模型、命名与安全声明是否规范、
合理、统一。没有证据的个人风格偏好不算发现；不一致必须给出具体 `METHOD /path`、规范位置、对照接口和客户端或调用影响。

审计报告增加“Swagger/OpenAPI 评审”一节，至少列出 operation 总数、未文档化/无实现的路由数、重复或不稳定的
operationId、路径与参数风格分组、公共 schema/错误契约复用情况及兼容性风险。若子树没有 HTTP API，明确记为不适用。

### 阶段 4 — 汇总

每条结论要有证据(文件、命令输出、依赖版本、git 统计),并按下面的格式分级。

## 报告格式

```markdown
## 审计范围
[仓库/子树]  [模块数、文件数、依赖数]
采样:...        未覆盖:...(说明为什么,以及漏判风险)
派出视角:...    跳过:...

## 结论摘要
三到五句话说清:这个仓库现在最主要的结构性风险是什么,以及最划算的第一步。

## 分级发现

### 已在造成损失
有证据表明**现在就在**产生成本的:线上缺陷、每次改动的额外工作量、无法诊断的故障。
每条:现象 | 证据 | 成因 | 代价 | 建议 | 大致成本

### 会在下一次踩到
当前没爆,但明确的触发条件已在路线图上或很常见。写明触发条件。

### 记录但不动
真实但代价低于修复成本的。**明确写"建议不动"及理由。** 这一节不是凑数,它是在阻止别人重复发现同一件事然后重复讨论。

## 依赖清单
表格:依赖 | 当前版本 | 最新 | 上游状态 | 许可证 | 是否可移除 | 建议

## 建议处理顺序
排好序的列表,每条注明依赖关系(哪些必须先做)。不要给"路线图",给下一步。
```

## 不要做的事

- 不要在没有具体坏现象的情况下建议重构
- 不要逐条给设计原则打分,不要清点设计模式数量
- 不要把"和我的偏好不同"写成发现
- 不要报告未采样区域的猜测结论 —— 说明没采样即可
- 不要自动动手改代码。挑出来要修的走 deep-review 的修复流程
