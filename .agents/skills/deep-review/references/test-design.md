# 验证设计:六维度提取与六种方法

从"需求 / 契约"推出"该验什么",再推出"怎么验"。

`deep-test` 在补缺口和设计不变量测试时读这一份;`deep-review` 在证伪阶段需要构造场景时读。

> **这是设计方法,不是必报清单。** 方法用来想到该验什么,报告里仍然只收拿得到证据的发现。

**顺序不能反:先按特性选方法,再用方法产出。** 反过来会产生大量形式正确但无意义的验证 ——
给一个只有两种取值的开关画判定表,给一个没有状态的对象画状态机。

---

## 一、六维度提取(先决定"验什么")

前五维从需求**正向推导**,第六维**反向核对**。

| 维度 | 产出 |
|:---|:---|
| **1 功能** | 每条能力的主路径:能进、能出、结果可见 |
| **2 业务规则** | 规则本身及其组合:满足、不满足、临界、多规则叠加时的优先级 |
| **3 边界条件** | 字段登记 + 逐类型取值,见 `boundaries.md` |
| **4 异常场景** | 每一步偏离主路径后的分支:失败、超时、拒绝、中断 |
| **5 非功能** | 性能(数据量/并发/指标/阈值/判定方式)、安全、兼容、可观测 |
| **6 高危模式比对** | 拿 `failure-patterns.md` 的 A 类八条**逐条**问:这次会不会撞上 |

**第六维是反向的,必须单独做。** 前五维是从需求里读出来的,而 A 类八条的共同点是
**它们通常不在需求里** —— 需求描述"应该怎么走",不描述"这条路整体失效会怎样"。

**判定为不触及也要留痕,写明理由。** 否则读者无法区分"评估过认为无关"和"根本没想到"。

**只能依据写明的规则划分,不能把自己的假设当需求。** 规则说"字母数字",那含下划线就属无效;
规则没说"不能纯数字",就不能凭空造一条"纯数字非法" —— 想加约束先去问,不要自己补一条再按它验。
**期望值定不下来的,按需求缺口报出来等澄清,不要用"与现状一致"糊过去。**

## 二、六种方法(再决定"怎么验")

| 方法 | 什么时候用 | 产出什么 |
|:---|:---|:---|
| 等价类划分 | 输入可分类 | 每类一个代表值 |
| 边界值分析 | 有数值/长度/时间边界 | 上点、内点、离点 |
| 判定表 | 多条件组合决定结果 | 条件组合矩阵 |
| 状态转换 | 有明确状态机 | 合法路径 + 非法转换 |
| 场景法 | 有业务流程 | 基本流 + 备选流 |
| 错误推测 | 兜底 | 经验高风险点 |

### 等价类划分

把输入域切成若干子集,同一子集内任取一值效果等价,于是用有限验证覆盖无限输入。

**有效类可以合并覆盖,无效类必须逐个单独覆盖。**
原因很实际:一次同时填入两个非法字段,系统只会报第一个错,**第二个字段的校验逻辑根本没被触达**。

### 边界值分析

缺陷聚集在边界上,不在区间中间。取上点、内点、离点;各类型的具体取值见 `boundaries.md`。

### 判定表

条件之间有组合关系时用。列出条件桩与动作桩,覆盖组合。

**判定表最大的价值不是产出验证,是暴露需求缺口** —— 填表时经常发现某个组合根本没定义
(两种优惠到底叠加还是取高)。这类发现要单独反馈,**不要自己臆断后当成需求写进去**。

条件超过四个时组合数爆炸,改用正交压缩,或只覆盖高频组合 + 边界组合,并写明裁剪依据。

### 状态转换

**覆盖要求**:每条合法转换至少一次;**每个状态到其余每个非法目标状态各算一项,逐条验证**;
终态的不可逆性(已完成的不能回到待处理)。

**非法转换是漏测重灾区** —— 需求只描述"应该怎么走",不描述"不能怎么走",而事故往往出在后者。

数量爆炸时可按优先级裁剪,但**裁掉的每一项都要写理由**。不接受"只验典型的" ——
"典型"由谁定义?那正是把该验的悄悄摘出去的另一种说法。

配合 `failure-patterns.md` A3:除了转换本身,还要验**在每个节点中断再进入**。

### 场景法

**基本流**:达成目标的理想路径。**备选流**:每一步偏离后的分支。

**经验法则:一条 N 步的基本流,至少产出 N 条备选流** —— 每一步都问"这里可能出什么问题"。

### 错误推测

前五种覆盖完之后的兜底,按经验列高风险点:

| 分类 | 典型场景 |
|:---|:---|
| 网络 / 服务 | 中断、超时、连接重置、5xx、名称解析失败 |
| 并发 / 竞态 | 重复提交、同时编辑、乐观锁冲突、幂等 |
| 数据 / 状态 | 脏数据、不一致、空结果集、主键冲突、引用失效 |
| 外部依赖 | 第三方超时、不可用、降级 |
| 认证 / 授权 | 凭证过期、会话超时、权限不足、越权 |
| 使用行为 | 快速多次触发、后退与刷新、中途关闭、粘贴 |

## 三、产出的硬规则

1. **一项只记一项。** 判据是:**这一项挂了,能不能单独看出来是它挂了。**
   把十几个场景塞进一个验证,数量好看但指不出是谁坏了。
   数据驱动(一组表格、每行各有独立期望)是合法的例外。
2. **每一项必须自足可独立执行。** 不许写"同上,换个字段" —— 那样计数好看,执行时却要跳回去找,等于不可独立执行。
3. **未覆盖项逐条列出。** 不接受一句"部分覆盖" —— 列出来的缺口是有价值的信息,一句"部分覆盖"什么都不是。
4. **每个期望要有独立 oracle。** 来自需求、契约或独立计算;**录下当前实现的输出当期望,等于把 bug 一起冻结进去。**
