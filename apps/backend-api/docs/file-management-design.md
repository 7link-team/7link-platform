# 通用文件管理与 Web 文件管理器实施方案

状态：基础方案与第 21 节扩展已获用户“继续”授权实施（2026-09-18）；未完成验收。日期：2026-09-18。
执行模式：Direct；两轮评审由主代理执行，不使用子代理。
基线：提交 `5396b20` 为 WIP，后端菜单目录响应类型尚有编译错误。
本文描述目标设计，不代表功能已实现、测试通过或产品已验收。

## 1. 目标与范围

提供本地/S3 流式存储、普通与断点传输、四摘要校验、受控秒传、虚拟目录树、
历史版本、回收站和桌面式 Web 文件管理器。迁移头像存储，移除 IAM 的
`AvatarDirectory` 配置及直接文件读写，保持后端注册随机生成、候选选择和上传裁剪。

用户已明确：合并、覆盖、移动、复制及批量逻辑变更必须整体原子，不能部分成功。
本方案不实现前端逐文件写入，也不使用后台小事务分段发布目录变更。

原第一版不做公共分享；用户现已要求密码/令牌共享，扩展按第 21 节待确认方案。
仍不做乱序并行上传、跨租户移动/复制、压缩包解包、全文索引、
任意格式转码和在线编辑。历史版本保留/回收站自动清理采用显式配置，不擅定期限。

## 2. 现状、复用和模块边界

- 后端已有 module 生命周期、ProvideServices/InjectServices、权限评估、审计、
  guid.ID、模块自有三方言迁移和类型化 query；按现有模式复用，不另建 DI 框架。
- organization 已有 parent_id + closure 部门树及版本冲突检查；复用模式，
  不跨模块直接操作部门表，也不直接复用未适配大规模的全量内存算法。
- minio-go 已是依赖；通用存储不能耦合审计归档的保留锁定规则。
- 没有通用文件模块；现有 IAM 头像直接落盘只是待迁移实现。
- 前端为 React/Vite/react-router，已有共享 UI、Lucide、裁剪组件和 Playwright。

新增 `internal/files` 自有生命周期、model、query、sql/{sqlite,postgres,mysql}。
仅 internal/app 负责组合。files 通过窄能力调用现有 IAM 权限服务；identity 注入
files 的受控对象能力，避免 files 与 identity 双向依赖。注册顺序、bootstrap 和
审核/审计依赖须经架构门禁验证。复用授权引擎，不创建另一套平行角色系统。

存储根目录、S3 bucket/endpoint 等归 files 配置；账号资源与租户资源分离。
API 服务器没有完整文件中转缓存，最终本地存储可以与服务同机，但必须明确是后端目的地。

### 2.1 可扩展存储驱动

用户开工后补充确认：参照网盘存储插件的边界，local、S3、原生 OSS 等可扩展。
采用应用级 DriverRegistry + DriverFactory（构造）+ Driver（运行策略），不用全局注册状态。
后端各自持有配置，不把 OSS 强制当 S3；仅协议兼容的 OSS endpoint 可使用 S3 驱动。
基础能力包括不可变对象写入、读取和删除；Range、multipart、服务端复制由显式能力合同
提供，不支持时返回 unsupported，禁止偷偷整文件缓存、重新上传或中转磁盘模拟。
业务记录 backend ID + 稳定对象位置，驱动切换不直接改写已有对象归属；凭据不进 filemeta。
驱动共享合同测试验证长度、取消、重试、超时、分片接管、范围读取和清理语义。

## 3. 数据模型

全部持久化实体使用 guid.ID，数据库 BIGINT，接口 JSON 十进制字符串。
虚拟名称、对象 URI、外部标识不得伪装成 guid.ID。

| 表 | 主要字段与职责 |
| --- | --- |
| file_spaces | scope_kind、tenant_id/principal_id、根节点、空间并发版本、配额；租户或账号隔离 |
| file_objects | 唯一存储位置、状态、长度、四种实际摘要、MIME/格式、元信息、创建时间 |
| file_nodes | space_id、parent_id、kind、name、name_key、ext、current_version_id、并发版本 |
| file_node_closure | space_id、ancestor_id、descendant_id、depth；包含深度 0 的自身关系 |
| file_versions | node_id、序号、object_id、ext、声明 MIME、作者、创建时间、来源版本 |
| file_uploads | 空间/所有者、长度、预期四摘要、偏移、四累计 hash state、状态、存储凭据、租约 |
| file_upload_parts | upload_id、分片序号、起始偏移、长度、存储凭据、确认状态 |
| file_trash_batches | 删除根节点、原父节点/名称、删除人/时间、状态；支持一次原子批量删除 |
| file_operations | 请求/幂等键、动作、策略、计划修订、状态、结果、资源成本、租约 |
| file_operation_items | 分页准备的操作计划、源/目标版本、冲突及决策；不是部分执行结果 |

物理对象一行对应一个最终存储对象，文件版本多对一引用；缩略图也是独立物理对象。
对象物理键使用不可猜测/ID 键，不使用虚拟文件名；物理位置约束唯一。
virtual node 的文件/目录同用一个名称空间。同目录活动名称键唯一；回收站不占原名称。
根节点唯一；所有 FK/查询都校验 space，防止跨空间连接。目录无文件版本，文件不可有子项。
快照、回收站和进行中的操作仍可能持有引用；清理不能只看 current_version_id。
file_uploads 另存 last_progress_at、expires_at、expired_at、release_state 和释放错误码；
file_upload_parts 保留有界管理记录和实际释放状态，不向管理页面暴露 hash state/存储凭据。

## 4. URI 与存储身份

通用存储位置采用 URI，适配器按 scheme 解析，不引入 avatar 专有路径配置：

- 本地最终位置：file URI，仅服务端可见，必须落在配置根目录内。
- HTTP/HTTPS URI：可表达稳定外部位置；不保存临时签名 URL，不直接当可信文件读取。
- S3 使用 bucket/key/version 的稳定定位信息；建议支持 s3 URI，不用过期签名链接定位。

IAM 保存受控文件引用 URI，不保存本机物理绝对路径；建议使用稳定 HTTPS 逻辑访问 URI，
具体契约在确认项中列明。访问时通过文件服务鉴权，签名 URL 是短时访问凭据而非持久引用。
外部 URL 抓取不在第一版；解析 URI 不等于允许任意 file 读取或远程 HTTP 请求。

## 5. 目录、归属和权限

选择 parent_id + closure：直接子项分页查询，祖先/子树与循环判断使用闭包表。
不持久化完整路径；路径由祖先生成，目录改名不改物理键。CTE 是查询方式而非表类型。
深度、操作节点数和闭包变更量必须受限，预算计入新旧祖先数与子树规模。

租户拥有空间，但普通成员不天然拥有全树读取权。有明确全空间管理权限的管理员可管理
全部；角色/部门/实体作用域使用现有 IAM 评估能力。工作区目录绑定部门或实体 ID，
它们是可包含子目录的节点，不是叶子，也不把组织树镜像成固定文件树。
组织调整不自动搬目录；被绑定主体停用/删除时禁止继承意外放宽，要求显式重新绑定。
账号头像放账号资源空间，不依赖租户成员身份。

操作权限包括列目录、读取/预览、创建、更新、移动、复制、删除、恢复、清空回收站和管理。
移动/复制检查源、目标和实际被替换对象；复制不能把无权内容带入可读空间。
不得通过路径、计数、搜索、缩略图或秒传泄露不可读节点；隐藏祖先时只展示授权工作区入口，
不能靠显示完整租户树获得可达性。继承/直接绑定适用范围需按现有 IAM 合同明确映射。

## 6. 命名与路径兼容

名称保存 Unicode NFC；冲突键由固定 Unicode 版本的规范化 + casefold 生成，
采用二进制比较，不依赖各数据库默认排序。大小写折叠后同目录不允许重名。
支持中文，拒绝路径分隔符、控制字符、Windows 禁用字符、尾部点/空格、`.`/`..`、
Windows 设备保留名（含带扩展名形式）。具体设备名集和边缘 Unicode 用夹具验证。

建议名称同时不超过 255 UTF-8 字节和 255 UTF-16 code units；最终相对路径长度另设预算。
自动重命名为 `名称 (n).扩展名`，预留后缀长度，不能破坏字符或仅靠预检查防重名。
非法名称返回可操作的错误，不静默改名。上传原始名称可留作来源属性但绝不能用作物理路径。
下载 Content-Disposition 使用安全 fallback 与 filename*，不承诺所有用户本地保存路径可用。
多文件夹打包下载不在第一版；单文件下载与后台文件复制是不同能力。

## 7. 普通上传、秒传和标准断点协议

普通上传使用原始请求体，不采用可能落临时文件的 multipart parser。
四个必需整文件摘要 header 为 X-File-MD5/SHA1/SHA256/SHA512，十六进制固定长度，
统一大小写解析；声明长度必需，超长/短写/空文件均明确检查。浏览器采用有界增量摘要库，
不能用整文件 arrayBuffer；哈希算法库须经依赖审查，不自行实现密码算法。

秒传是单独的授权匹配请求，匹配长度 + 四个服务器已验证摘要。
只允许复用请求者当前可读对象对应的有效引用；无权限和未匹配返回同类未命中结果。
不向外泄露对象存储键；MD5/SHA1 不提供安全保证，S3 multipart ETag 不当整文件 MD5。

断点上传采用 tus 1.0 顺序 POST/HEAD/PATCH/DELETE/OPTIONS，不声称四摘要 header 是标准。
POST 固定绑定预期摘要、长度、所有者与空间。PATCH 使用 Upload-Offset、
application/offset+octet-stream；重复/错偏移不能二次追加。HEAD 返回已确认进度。
四摘要在所有传输 PATCH 上校验一致，HEAD 不要求客户端重传敏感凭据。
协议 checksum 扩展若支持，用于当前请求体校验，与整文件摘要明确区分。
扩展能力只广告实际实现的内容，严格检查 Tus-Resumable 与跨域暴露头。

每次已提交 checkpoint 同时保存 offset + 四种累计 hash state + 分片凭据。
hash state 使用 Go 标准 hash 的序列化能力，带格式/实现版本和完整性校验，客户端不可提供。
实现版本不兼容、状态损坏时 fail closed，不伪造进度也不拿分片摘要拼整文件摘要。
最终四摘要全部匹配且物理对象可确认，才能发布虚拟引用；不匹配不得秒传或预览。

S3 每个非最终提交片不少于 5 MiB，分片数量/大小符合供应商限制；客户端按后端广告
的切片规格发送。PATCH 边界与协议互操作性须明确，不能声称无限制 tus 通用客户端兼容。
确需适配小 PATCH 时只允许固定上限的缓冲，禁止不受限内存和服务器临时磁盘。
stock tusd S3 store 的临时磁盘行为不满足要求，不可直接采用；优先复用协议 handler，
但实际 handler、SDK、签名和重试路径需验证不隐藏缓冲/落盘，未验证前不确定最终依赖。

## 8. 存储/数据库故障恢复

上传每会话单写者：持久租约、fencing token 和 offset/version CAS 防止并发覆盖。
仅在最终后端确认写入后提交 checkpoint；请求断开允许返回最后已确认偏移。
本地后端重启校验长度，截断未提交尾部；同步文件后才能确认进度。
S3 重启列出/核对分片与持久记录，不发布未确认片，不允许过期写者覆盖已确认 part key。
数据库 fencing 本身不能撤销已经发给 S3 的请求。发生租约接管且旧请求无法确认终止时，
冻结当前 multipart attempt，先完成存储对账；不得在同一 upload ID/part number 上抢写。
必要时新建隔离 attempt，经预算内的服务端分片复制恢复已确认内容；若供应商能力不足，
明确暂停/失败，不谎报可无条件接管。该机制是 S3 验收门禁，不用只测 DB CAS 代替。
超时导致完成结果不明时核对唯一对象 key/长度/元信息，确认后幂等结束，不能盲目重传覆盖。
会话先完成物理确认，再以数据库事务发布；崩溃后 HEAD/任务查询可恢复结束状态。

### 8.1 后台分片列表与超时释放

提供上传会话列表及会话下的分片分页列表，展示所属空间、用户、名称、总长、已确认偏移、
分片序号/长度、状态、最后进展时间、到期时间和资源释放状态。支持按用户/空间/状态/时间
过滤；租户管理员只查授权租户，平台运维须通过独立平台入口且有明确权限并留审计。
存储地址、multipart 凭据和序列化 hash state 不返回 Web；普通用户可查看自己的传输状态。

超时采用可配置的无有效进展期限；只有成功提交非空数据 checkpoint 更新 last_progress_at，
HEAD/列表轮询、错误请求和重复空请求不延期。期限数值待确认，建议以 24 小时为初始值。
新会话以创建时间起算；每个流请求还有最大执行时间，不能靠长连接无限占用存储资源。

到期即不可再续传：API 和清理器都以服务端时间检查 expires_at，不依赖定时器是否及时运行。
清理器 CAS 认领过期状态并阻止新提交，失效上传返回 410 及明确的 restart_required，
客户端清除旧续传记录，重新创建会话，从偏移 0 上传；即使字节尚未物理清除也不允许恢复。
旧会话不为新会话提供内部分片复用；之前已独立完成且授权的对象仍可走正常秒传。

本地删除会话的未发布最终后端临时对象，S3 AbortMultipartUpload，释放 hash state、分片
存储及未完成容量预留；有界审计摘要保留，容量确认释放后才从实际占用中扣除。
释放失败状态为 pending/failed，可重试但会话仍永久失效。到期与 PATCH/finalize 并发
通过会话版本/租约串行裁决，迟到 I/O 不得重新发布过期会话；完成对象与过期对象不能误删。
必要时延后物理删除直到旧写入终止/对账，维持逻辑立即失效、物理最终释放。

零引用对象清理使用状态机与引用检查，先标记清理 claim，禁止新引用，然后删除存储并记账。
引用创建和清理 claim 必须锁定/CAS 同一个对象记录，不能仅靠定时 count 后删除。
下载请求使用有期限读取保护；签名链接若后续采用，须让清理延迟覆盖其最长有效期。
删除失败可重试；任何任务、上传、版本、候选和缩略图引用都必须考虑。
数据库与 S3 无共同事务，不声称物理删除原子。任务清理错误不会回滚已提交目录操作。

## 9. 下载和安全预览

GET/HEAD 支持 Content-Length、Accept-Ranges、强 ETag 和 Last-Modified；
Range 支持起止、开放结束与 suffix，206/Content-Range、416 和 If-Range 正确实现。
第一版支持单 Range，多 Range 明确忽略并返回完整 200，不错误返回部分内容。
续传绑定不可变版本；使用 node 当前版本链接时需 If-Range 防止更新后拼接不同内容。
本地/S3 均流式读取，不整文件加载。取消传播到存储请求，预算与并发限制覆盖下载。

预览授权同内容读取；音视频使用 Range，文本有字节预算，缩略图懒加载。
HTML/SVG/可执行内容不在主站直接内联；原文件强制下载或安全隔离，设置 nosniff。
未知格式显示属性/下载，不运行用户文件；不声称浏览器支持所有编码或 DRM。

## 10. Filemeta 注册表与策略

统一探测器 + 可注册提取器策略，不引入复杂工厂层。Input 含声明属性和受预算控制的
Reader/ReaderAt，Extractor 可声明支持类型、所需读取预算与版本；输出结构化结果。
顺序流入时保留固定上限前缀，只有明确预算允许时通过最终存储小范围读取补充，
不为 metadata 扫整文件。大文件无需加载完整内容，无论视频还是 APK。

| 位置 | 属性 |
| --- | --- |
| file_objects | detected MIME、type/subtype、format、size、四摘要、探测依据 |
| file_objects | width/height、duration、codec 等可取得的可空结构化属性 |
| file_objects | metadata_json、提取器版本、状态/错误码、缩略图对象引用 |
| file_nodes / file_versions | 当前/历史 ext、显示名称、客户端声明 MIME 和来源属性 |

扩展名取规范化最后一个后缀，可另存组合后缀；客户端 MIME 与探测 MIME 分开。
未知、预算超限、不支持和提取失败明确区分；元信息提取失败不必使有效文件上传失败。
常用查询字段建组合索引；格式专属字段留 JSON，三方言保持语义一致，不默认全文扫描 JSON。
默认不提取 GPS/全部 EXIF 等隐私数据；搜索仅筛选授权范围。
### 10.1 扩展名伪装与改名

`1.mp4` 改成 `2.mp3` 或 `4.apk` 只更新 node 名称/ext 和当前名称匹配提示，
不改 file_objects 的 detected MIME/type/subtype/format、尺寸、时长、摘要或缩略图。
改名不触发重新解码；只有新内容上传形成新物理对象，或显式按新提取器重跑时才更新探测信息。
历史版本来源 ext 不改写，页面显示当前名称与实际检测格式。

提取器路由优先采用可信程度更高的内容探测；扩展名只作辅助，不作为启用高风险解析的依据。
声明 MIME 同样不可信。记录 detected_format、detection_basis、detection_status，
前端/搜索响应计算当前 ext 与检测类型的匹配状态（matched/mismatch/unknown），不能在
共享物理对象上存某个虚拟名称的全局 mismatch。普通改名不影响其他虚拟映射。

检测是有限预算的最佳努力：文件头可能被伪造或存在 polyglot，MP4 容器不保证是视频，
ZIP 文件头不足以确认 APK；预算内无法确定就记 unknown/container，不假装准确识别。
不因扩展名不同自动删除或重写内容，也不把 mismatch 等同恶意文件。
预览/播放以检测内容与浏览器支持能力为依据，无法安全确认时仅下载；
HTTP Content-Type 不采用可疑后缀推断，unknown 用 application/octet-stream，配合 nosniff。
头像属于单独的输入规则：必须实际解码为允许的栅格图并重新编码，不能靠改后缀绕过。

建议初始前缀预算 256 KiB、额外读取预算 1 MiB；缩略图像素和执行时间独立受限。
尺寸元信息不等于可安全解码：超大像素、解压炸弹应跳过缩略图，保留已探测属性。

## 11. 历史版本与回收站

file_versions 不可变，node 指向当前版本；覆盖保留目标 node ID，追加版本。
文件扩展名在改名后更新当前 node；历史版本的来源 ext/声明 MIME 不随当前改名改写。
恢复旧版本也创建新版本，可审计，不改历史。移动/改名不复制物理对象。
复制默认只复制当前内容并生成独立 node/version，不继承源全部版本/个人授权绑定。
历史内容的访问权限跟随当前节点评估，不保留已撤销权限的旧授权。

回收站以批次隐藏删除根及后代，所有列表、路径、搜索、下载和权限查询统一考虑祖先删除。
软删活动名称槽释放，原父/名保存于批次；内部父子结构保留。
恢复整体事务执行，原父失效时选授权目标；同名必须按明确冲突策略处理。
清空将可恢复逻辑引用整体解除，物理清理异步；原子性不扩展到不可撤销的远程物理删除。
保留上限、自动清空期限、候选和上传过期时间均属配置，确认前不启用隐式销毁。
同时显示逻辑使用量与实际物理量，计入历史、回收站、未完成上传的预留容量。

## 12. 实时单事务批量操作与冲突

2026-09-18 用户修订：复制和移动为实时请求，不建立持久化冲突/决策工作流。
该修订优先于此前 queued/preparing/awaiting_decision 方案及历史检查点的下一步。

POST 操作接受源节点 ID 集合、目标目录、动作、冲突策略和幂等键，同步返回最终结果。
后端去重父子选择，按需分页读取并有界检查成本，不全树塞请求或无限数组。
需要询问时返回本次检测到的冲突，不创建待决策任务、不保存冲突表/决策表、不持有
事务等待用户点击。用户确认后带明确策略和已观察的版本重新提交请求；后端重新
鉴权、检查源内容/节点/目标版本与冲突。变化时拒绝并返回最新冲突，不能擅自覆盖。
检查不代表占用目标名称；最终所有逻辑变更必须在同一事务内重新验证并发布。

真正执行所有虚拟变更、版本、回收站、审计及成功结果走一次事务，SQL 可批次发出但
不分段 commit。存储准备不在这条长事务内，提交时不得执行网络存储 I/O。
SQLite 写事务 + 空间版本校验、其他方言锁定/CAS按一致顺序执行，防止计划快照过期。
权限撤销的并发一致性必须与 IAM 既有约束协调，不能只在准备阶段检查。
事务失败完全回滚，不能给出逐项成功。响应丢失后的幂等结果与审计沿用项目现有能力，
不为冲突新增生命周期/租约/清理机制，不把同步结果伪装成后台受理成功。
已有内部操作/快照模型需要在接同步 runner 时审查复用边界，不在本次修订中删除
既有迁移或用户数据；它们不是公开实时复制/移动的待决策接口契约。

| 冲突 | 支持策略 |
| --- | --- |
| 文件与同名文件 | 覆盖为新版本、跳过、自动重命名、询问 |
| 目录与同名目录 | 递归合并、替换整个目录、跳过、自动重命名、询问 |
| 文件与同名目录或相反 | 明确替换、跳过、自动重命名、询问；不允许合并 |

目录合并将源内容递归纳入目标，同层文件和目录再应用对应策略；允许应用到全部同类冲突。
目录替换/类型替换将旧目标入回收站再放新节点，同事务内完成，旧物理文件不先删。
移动合并只移动成功采用的项，跳过项保留源处；整次决定与变更原子提交。
整体替换导致被删目录中的授权绑定不能自动转给新目录。
自身、子目录、源目标交叠的危险操作拒绝；跨空间操作第一版拒绝。

有限规模单事务是硬约束；实时操作超限拒绝，不隐式改为后台队列或部分成功。
建议初始可配置上限：深度 64、操作 10,000 节点、闭包变更 500,000 行、提交 30 秒。
最终必须经 SQLite/真实存储压测校准；超限拒绝并给出原因，不偷偷拆成部分成功。

## 19. 两轮评审记录

两轮为主代理顺序自审，不声称独立第三方评审；均是设计评审，不是运行测试。

### 第一轮：架构、原子性与恢复

| 发现项 | 结论与修订 |
| --- | --- |
| 一次事务与大目录分批执行的旧方案冲突 | 采用事务外分页计划 + 一次事务发布；禁止分段 commit，超限拒绝 |
| 数据库事务无法回滚 S3 物理删除 | 新内容先准备，提交只切逻辑引用；旧内容保护并异步清理 |
| DB 租约不能阻止已发送的 S3 迟到写入 | 加入冻结 multipart attempt、对账与隔离接管门禁 |
| 准备过程中源内容可能变化 | 计划固定版本、节点/空间 revision，变化重规划，不混合快照 |
| GC count 与新引用有竞态 | 同对象记录 CAS/锁定清理 claim，并保护任务、候选及下载引用 |
| commit 成功但响应丢失可能重复执行 | 最终结果同事务落库，幂等键查询恢复 |
| stock tus S3 暂存及分片限制 | 不采用磁盘 spool；明确客户端分片规格及真实流式验证门禁 |

结论：上述发现已修订到方案。S3 SDK 实际路径、三方言锁语义和吞吐仍需实施验证，

## 20. 实施检查点（2026-09-18）

本节仅记录已实现的基础能力，不改变第 17 节完整产品验收门禁。

- 原子复制/移动的准备与提交复用同一策略遍历器。准备使用有界、按需读取的
  内存视图，占位批次生成的名称，模拟合并、替换、跳过和移动后的树状态；
  不写入用户节点、版本、闭包或回收站。每页数据库读取不超过 100 行。
- 迁移 8 保存节点/闭包累计成本及预期结果计数。超限不进入 ready；执行仍独立
  检查预算、版本和权限，实际结果成本不一致则整体回滚。旧/损坏成本计划不可执行。
- 非 SQLite 操作空间与计划使用类型化 SELECT FOR UPDATE；SQLite 先无操作写锁，
  再读取验证存在性与版本，不依赖 MySQL 的 changed-rows/clientFoundRows 设置。

## 21. 层级范围、文件 ACL 与共享扩展设计稿

状态：IMPLEMENTATION AUTHORIZED。设计稿交付后用户要求“继续”，按三项推荐选择执行。

本节优先于原方案的公共分享排除项与尚未具体定义的工作区权限规则。

### 21.1 目标、现状与复用

用户确认：超管可看全部文件；租户级管理可看租户内全部实体及子集文件；实体级
管理可看本实体及子集文件。该范围内不同账号还需要不同的文件/目录访问权限。
支持账号个人文件、租户/实体/部门工作区及四种密码/令牌共享。

现有代码有 account/tenant Space、Node/closure、不可变内容版本、回收站与同步
批量引擎；没有实体/部门/个人工作区归属、持久化目录 ACL 或链接共享。Web 浏览
组件已存在，但生产页无授权 loader。EntityConstraintOn 为新增未完整验收能力；
当前 operationService 只接受租户和实体 claims，不能直接覆盖平台或账号入口。

复用现有 IAM 的平台/租户/实体授权、部门数据范围、账号、角色、组及策略 revision。
DataConstraint.ResourceIDs 是 IAM 实体 ID，不是文件节点 ID；Ancestors 仅为授权
来源，不由 files 再展开。文件模块不复制 IAM 实体树或另建角色/组织成员表。
复用 passwordx、审计、限流、模块能力注入、三方言迁移和 OpenAPI 生成链路。
执行模式 Direct；当前边界与接口尚紧密耦合，不使用子代理。

### 21.2 存储空间与组织文件根

保留 account/tenant 两类内部数据分区，不作为公共 API 或 Web 业务概念，也不为每个
实体/部门另建物理存储驱动。文件根是 `kind=directory` 的普通文件资源，通过
`root_scope + root_owner_id` 标识归属；不新增 Workspace/Root 表或资源。

| 文件根 | 所有者 | 整体权限来源 | 推荐管理读取范围 |
| --- | --- | --- |
| 账号独立个人根 | Principal | 账号本人 | 本人；平台全局读取，不开放给任意租户管理员 |
| 租户内个人根 | Tenant + Principal | 租户内本人 | 本人；本租户的显式管理读取 |
| Tenant 根 | Tenant | Tenant 范围 IAM 角色权限 | 本租户管理读取 |
| Entity 根 | Entity | Entity 范围 IAM 角色权限 | 本实体及明确授权的上级管理读取 |
| Department 根 | Department | Department 范围 IAM 角色权限 | 本部门及明确授权的上级管理读取 |

账号独立个人根与租户内个人根不能混同：同一账号加入多个租户，不意味着
这些租户均能读取其账号独立文件。用户已确认两类个人文件边界均需保留。
部门必须验证真实租户/实体绑定；不能仅因数字 ID 相同或界面当前实体而认定归属。
Tenant/Entity/Department 根属于对应组织，不属于创建人；创建者只进入审计记录，离职、
停用或调岗不改变根归属。根创建和绑定必须与组织资源在同一事务提交，普通接口不得
重绑定，组织停用时也不得退化为租户公共目录。

### 21.3 授权判定与管理读取

普通登录访问同时满足：认证身份有效、资源状态允许、IAM 动作能力与组织数据范围、
该节点有效 ACL、操作涉及的祖先遍历及源/目标检查。IAM 角色权限是整棵组织文件树的
能力上限，ACL 只做目录/文件细分，不能突破组织边界、绕过 IAM 显式拒绝或给无业务
动作能力的账号授予管理能力。即：`允许 = 范围合法 AND IAM(action) AND ACL(action)`。

建议独立设置“查看全部文件”管理读取能力，限定平台/租户/实体/部门范围，绕过
该范围内普通文件 ACL 的读取拒绝与继承中断，以兑现用户的上层可看全部文件要求。
不是按账号层级无条件放行；该能力可单独配置给管理账号，不赋予同层级所有账号。
此例外不覆盖 IAM 硬性拒绝、停用状态、跨租户边界；不自动附带写入、删除、分享或
修改权限。平台能力只在独立平台入口使用，不注入普通租户会话。
下级 ACL 是否可限制管理读取属于待确认产品选择，不能在实现时自行决定。

每次动作独立评估；前端接收当前节点 capabilities，仅用于控制按钮，后端仍须鉴权。
属性页展示有效权限、直接/继承来源及管理读取来源，仅向有权限的人提供解释。

### 21.4 Linux 风格 ACL，不照搬 chmod 数字

| 权限 | 实际约束 |
| --- | --- |
| list / traverse | 列举直接子项 / 穿过目录；traverse 不泄露该目录的其他内容 |
| read | 读取内容与预览；元信息按独立可见性控制 |
| download | 提供附件下载入口；不能承诺阻止有 read 权限的人保存已读取内容 |
| create | 在目录内创建文件、上传、创建子目录 |
| update | 更新文件内容、覆盖追加版本 |
| rename / move | 修改名称；移动检查源节点、源父目录及目标目录 |
| delete / restore / purge | 删除、恢复、永久解除逻辑引用，分别授权 |
| share / manage_acl | 创建共享 / 修改权限，均不能超出自己的可委派权限范围 |

ACL 主体为账号、部门、用户组和角色；主体 ID 复用 IAM。组织文件根的 owner 是
Tenant/Entity/Department 本身，不是创建者 ACL。个人文件根才以 Principal 为 owner。
每条规则包含动作集、allow/deny、适用于自身/后代和是否继承。
目录默认继承，目录和文件均可设置停止继承；有效链截止最近继承中断点。
普通访问在有效链内显式 deny 优先于 allow；无匹配 allow 默认拒绝。
要撤销父目录 deny 对某个子项的影响，必须有权限地中断继承，而非添加子项 allow。
组织根基线由其 `root_scope/root_owner_id` 与对应范围 IAM 权限共同产生，不写入创建者
规则。子项没有直接 ACL 时继承该基线；设置继承中断后必须由该子项 ACL 明确允许。
个人根显式配置 owner 权限。旧节点缺少根归属时禁止隐式放行，提供审计化绑定迁移或
管理修复入口；不得仅为启用旧数据创建全员读取规则。

权限管理不可给自己或别人授予超过当前可委派上限的动作；不能以 manage_acl
间接获得 purge/share。继承修改、组织成员变更和停用后有效权限必须及时重算。
有权的深层目录可作为独立工作区入口，不展示其不可见父目录名称或兄弟项。
列表、搜索、路径、计数、版本、回收站、缩略图和秒传统一过滤；先过滤再分页，
不能全空间查出结果后仅在 Web 隐藏，也不能因过滤后空页提前宣布查询结束。

### 21.5 移动、复制与权限继承

复制创建新节点，不复制源的直接 ACL、共享链接或所有者特权；继承目标目录 ACL。
移动保持节点身份、直接 ACL 和共享 ID，但继承链随目标目录变化，必须重新评估。
文件覆盖保留目标身份与 ACL，追加版本；合并保留目标目录 ACL；整体替换的新节点
继承目标父目录，不接收被替换目录的 ACL 或共享链接。

工作区根不得用普通移动变更组织归属；跨工作区移动需显式归属变更授权和影响确认。
第一阶段拒绝跨工作区移动/复制，后续按确认的归属转移规则扩展，不静默切换所有者。
移动/复制必须检查受影响子树及替换对象，任何拒绝整批回滚；不部分成功。
ACL 修改与操作共用文件空间锁/revision，IAM 与文件锁固定顺序；幂等重放仍重新
检查读取权限。同步 cost 仅用于内存预算和模拟/执行一致性，持久化 plan_json 不作为
新实时接口依赖；旧模型/迁移兼容另行审查，不删除已有迁移或原数据库字段。

### 21.6 四种共享与访问边界

| 验证方式 | 临时 | 长期 |
| --- | --- | --- |
| 密码 | 随机链接定位符 + 密码，expires_at 必填 | 随机链接定位符 + 密码，expires_at 为空 |
| 令牌 | 持有高熵随机令牌即可访问，expires_at 必填 | 持有高熵随机令牌即可访问，expires_at 为空 |

长期表示无自动到期，不表示不可撤销。单条共享绑定一个文件或目录，不使用账号
登录 token。匿名访问是推荐待确认选项；若只做内部共享，另加登录身份与组织约束。
建议第一阶段只开放浏览/读取/下载，不开放匿名上传、修改、删除、再分享或权限管理。
如需上传，需另外明确配额、内容隔离和滥用防护，不能直接复用登录用户上传接口。

密码用既有 passwordx Argon2id 哈希；随机令牌仅保存安全摘要，使用系统安全随机源。
令牌只在创建/轮换时显示，不保存明文以便“再次复制”；丢失后轮换并使旧链接失效。
密码通过 POST 验证，不进 URL；链接凭证交换短期、仅限该 share 的会话，浏览器
使用受保护 cookie，非浏览器使用专用授权头；不改变账号 session 或平台权限。
每次共享请求仍检查 share 状态、到期、凭证修订、根节点状态和当前发布者有效授权，
短期会话不能绕过撤销；到期由请求判断，不依赖定时清理保证失效。
链接令牌不写入审计/访问日志，避免 query、Referer 和第三方资源泄露；页面 no-store、
no-referrer，错误统一，不向未验证访问者泄露文件名；限流先于昂贵密码哈希验证。

共享是发布者受限委派，而非接收人获得整个组织范围。共享动作必须同时受共享配置、
发布者当前可委派动作/组织范围与节点权限限制，根授权撤销则整条链接不可用。
目录子项独立检查，中断继承或拒绝导致无权项隐藏，不能共享根后无条件放开子树。
新增子项跟随当前权限；共享跟随当前内容，不默认开放历史版本或回收站。
删除/替换的旧节点链接失效；移动后重新评估归属和发布者权限，不沿用过期授权。
共享撤销阻止后续请求，不承诺收回已下载内容或已发送字节；如使用存储签名 URL，
必须明确短时残留窗口，不能宣称立即撤销。首版建议通过授权网关流式下载。

## 22. 组织归属方案复审与实施状态（2026-09-19）

本节固化用户对组织文件所有权的最终纠正，并取代 21.12 中仍以“工作区”描述的旧检查点。
公共 API 和 Web 不引入 Workspace、Node、Space 或独立 Root 资源；它们只暴露统一的
`/files` 文件资源，目录也是 `kind=directory` 的文件。内部 `file_spaces` 仅负责租户与
账号数据隔离，`file_nodes` 仅是持久化实现名。

### 22.1 最终所有权与初始化规则

| 根类型 | 持久所有者 | 创建时机 | 创建者权限 |
| --- | --- | --- | --- |
| Tenant | Tenant | Tenant 创建事务内同步创建 | 仅审计，不自动授权 |
| Entity | Entity | Entity 创建事务内同步创建 | 仅审计，不自动授权 |
| Department | Department | Department 创建事务内同步创建 | 仅审计，不自动授权 |
| 租户内个人 | Tenant + Principal | 首次真实使用时幂等创建 | Principal owner ACL |
| 账号独立个人 | Principal | 首次真实使用时幂等创建 | Principal owner ACL |

组织根不会随创建者离职、停用或调岗而改变。组织成员能否进入整棵文件树，由对应
Tenant/Entity/Department 范围的 IAM 角色权限决定；子目录和文件 ACL 再做更细的
allow/deny 与继承控制。ACL 不能授予 IAM 已拒绝的动作。`file_read_all` 只允许在已验证
管理范围内绕过普通读取 ACL，不附带 create/update/delete/share/manage_acl。

Department 现在必须显式属于一个 Entity，父子 Department 必须属于同一 Entity。
兼容迁移允许旧记录暂时为 NULL，但它们在修复前不能创建或访问 Department 文件根，
不得根据当前界面 Entity 或相同数字 ID 猜测归属。

### 22.4 账号独立入口合同

账号、租户和实体文件使用同一文件资源模型，但通过规范路径显式表达作用域；服务器不接受
body/query/header 中可伪造的 owner 类型或 owner ID：

| 请求上下文 | 解释 | 授权 |
| --- | --- | --- |
| `/me/files` | 账号独立文件上下文 | 当前认证 Principal 自有 account space + owner ACL |
| `/tenants/{tenant_id}/files` | 租户文件上下文 | 租户级 IAM ceiling + 文件 ACL |
| `/tenants/{tenant_id}/entities/{entity_id}/files` | 实体文件上下文 | 实体权限网关 + 事务内 IAM ceiling + 文件 ACL |

账号上下文不得列出或按 ID读取 tenant space；租户上下文不得列出或按 ID读取 account
space。创建根仍使用 `POST /files` multipart：租户上下文只接受 `scope=personal`，账号上下文
只接受 `scope=account`。GET 不隐式创建根。账号根绑定账号空间的物理根目录，按需且幂等
创建；根 ACL 只授予对应 Principal 的 owner 主体。账号文件审计使用现有 tenant_id=0
审计链并记录 Principal，不借用任何租户 ID。

Web 的 `/me/files` 是账号控制台页面路由，不是另一套后端资源；它调用 `/me/files` API。
租户和实体文件页分别调用与页面作用域一致的规范 API 路径。切换各类页面必须清除旧选择、
路径和迟到响应，不能把一个上下文的授权快照显示到另一个上下文。

## 23. 全系统文件治理设计稿（2026-09-19）

本节承接“所有持久化上传统一走文件模块、按最低有效粒度归属并消除游离文件”的要求。
平台级全局逻辑/物理查看已明确延期，不属于当前实施范围。此处的“实例”按既有组织模型的 Entity
（实体）理解；部署实例或应用实例不是同一资源，若以后需要必须另行定义归属。

### 23.1 统一边界与强制不变量

统一治理覆盖用户或业务运行时产生并需要持久保留的内容：文件管理器文件、头像、商品图、
富文本图片、合同/工单/订单附件、导入源文件、需要留存的导出结果等。源代码静态资源、
部署配置、密钥、数据库备份、运行日志和临时进程文件不伪装成业务文件，仍由各自基础设施治理。

所有受管内容必须同时满足：

1. 字节写入只通过 files Driver 和暂存协议产生 `file_objects`，业务模块不得直接拼接磁盘/S3 key。
2. 长期对象必须被不可变 `file_versions` 引用；业务托管文件还必须有有效业务绑定。
3. 每个逻辑文件都能经已验证祖先路径解析到唯一归属根；客户端不能提交任意 owner 逃逸归属。
4. 读取只接受逻辑 `file_id` 或受控业务资源入口；storage key、URI、object ID 均不是普通下载凭证。
5. 暂存对象有明确截止时间；到期后按声明、加锁、复核、删除的有界流程回收，不能永久游离。
6. 物理删除前必须确认无 Version、业务绑定、同步操作 pin、上传/清理 claim 或合规保留。

`file_objects` 是全局物理事实，不声明 Tenant/Entity/Principal 所有权：同一物理对象可能被多个
逻辑版本引用。归属、名称、目录、权限、业务用途和生命周期属于逻辑层，不能下沉到对象行。

### 23.2 最低有效归属

服务器从已验证的业务资源和调用上下文推导归属，不让上传者为了省事自行选择更高层级。
Department 比 Entity 更细，因此仍保留；Entity/Department/租户内个人根继续位于所属 Tenant
space，不为每个组织资源创建物理 bucket 或新的公开 Workspace 概念。

| 最低归属 | 使用条件与示例 | 普通文件管理器 |
| --- | --- | --- |
| system | 平台拥有且不属于任何租户的运行时模板、全局素材 | 不进入普通文件管理器；由对应业务入口访问 |
| tenant | 多个 Entity 共同使用的租户文件、租户级模板 | 租户文件入口展示 |
| entity | 商品、订单、项目等明确属于一个 Entity 的文件 | 对应 Entity 入口；业务托管项默认隐藏 |
| department | 明确由一个 Department 管理的资料 | 对应 Department 入口；业务托管项默认隐藏 |
| personal | 某 Tenant 内 Principal 的个人工作文件 | 该租户个人入口展示 |
| account | 与任何 Tenant 无关的账号私有文件、Principal 头像 | 账号入口；头像等业务托管项默认隐藏 |

`system` 需要一个内部 system space；Tenant 继续一租户一 space，Entity/Department/personal
是其中的归属根；account 继续一 Principal 一 space。静态部署品牌资源不因 system scope 被强制
迁入数据库。资源从细粒度迁往粗粒度必须是显式、审计化归属变更，不能通过普通 move 完成。

System space 由受唯一约束的 `system_slot=1` 表示，`tenant_id` 与 `principal_id` 必须同时为空；
system 根直接由该 space 的物理根确定，不伪造 Tenant、Principal 或 `root_owner_id`。三方言升级
保留既有 Tenant/Account space；只要仍有 system 数据，降级到不认识 system 的旧结构就明确失败，
绝不把 system 文件静默改属或删除。

上传入口必须携带或由业务路由确定一个已注册 purpose。Purpose 合同声明允许的 owner scope、
MIME/大小、单值或多值、是否固定版本、保留规则和生命周期责任。例如 Principal avatar 只能
绑定 account scope；Entity 商品图不能写入 Tenant 根；Department 附件不能借当前 Entity 猜归属。

### 23.3 用户文件与业务托管文件

逻辑文件分为 `user-managed` 和 `resource-managed`，二者复用 Node/Version/Object，不另建文件系统：

- `user-managed` 由用户在有权限的目录创建，可合法存在而不绑定业务对象。
- `resource-managed` 由头像、商品、工单等业务资源持有，必须在创建逻辑文件/首版本的同一事务
  建立有效绑定；普通文件创建 API 不能伪造此模式或 purpose。
- 业务托管文件默认不出现在普通目录列表，避免系统附件污染文件管理器，也避免用户 move/delete
  破坏业务记录；对应业务页面仍能按业务权限查询、预览、版本化和审计。
- 一个业务文件可按 Purpose 合同允许多个引用。业务解绑只撤销该引用；最后一个引用消失后进入
  保留/回收流程，不能直接删除仍被 Version、其他业务资源或操作 pin 引用的物理对象。

建议新增唯一的 `file_resource_bindings` 作为 files 模块引用账本，而不是为每种业务复制一套
上传元数据。最小字段为 logical file ID、可选固定 version ID、注册 purpose、resource kind/ID、
slot、状态、创建/失效时间和并发版本。`resource kind + purpose` 必须来自启动时注册表；未知字符串
拒绝，不能演变成无校验的多态垃圾桶。业务模块仍保留自身业务关系，但文件的生存引用以该账本
为准，并通过模块窄能力在业务事务中原子更新。现有 avatar object reference 需迁移到逻辑文件与
绑定，不继续作为第二套长期模型；迁移必须保持原有候选过期和账号注销语义。

### 23.4 平台级全局查看（延期）

当前阶段不实现全局逻辑文件 API、物理对象 API、跨范围内容读取权限或平台 Web 管理页面，也不为
这些未来能力预注册权限。`GET /files` 只保持既有账号/组织授权范围，不能通过 query、header 或超管
身份切换成全局查询。普通文件接口不返回 object ID、storage key 或 URI。

未来确需全局查看时，应作为独立设计重新评审 URI、平台权限、字段脱敏、分页、查询计划和审计；
全局元数据查看与实际内容读取仍必须分权。延期不影响当前 Object/Version/Binding 数据完整性、
归属约束、业务入口读取、游离检测和清理能力。

### 23.5 游离检测、回收与规模约束

游离状态必须分类，不能用一个 `ref_count=0` 立即删除：

| 类型 | 判定 | 处理 |
| --- | --- | --- |
| 暂存游离 | Preparation 到期且未原子附着 | claim 后复核并回收存储写入 |
| 物理游离候选 | Object 无 Version/Binding/Pin，且无进行中 preparation/保留 | 隔离期后再次事务复核再删 |
| 逻辑业务游离 | resource-managed Node 无有效 Binding | 管理告警并隔离，按 Purpose 保留策略修复/回收 |
| 引用悬空 | Binding 对应业务资源不存在或已越界 | 禁止读取，告警；由 owning module 对账修复 |
| 用户未归档文件 | user-managed Node 无业务 Binding | 合法状态，不算游离 |

对象、版本、绑定和清理 claim 的状态转换必须可重试且对不确定提交保守；存储 I/O 不持有长数据库
事务。删除采用有界 keyset 扫描和双重检查，不做停服全表扫描。至少增加 Binding 的 resource/slot、
file/state 索引，Object 的 state/id 扫描索引，并复用 Version object 索引；反向引用计数批量聚合，
禁止逐行 N+1。真实 MySQL/PostgreSQL 必须分别验证大规模执行计划和并发 attach/detach/cleanup，
才能声称统一文件治理生产就绪。

到期 Binding 由现有 files worker 以 ID keyset 有界扫描；每条状态变更仍获取对应 Space 写栅栏并
推进 revision。与人工解绑并发时，已完成的状态变更视为幂等完成；其他错误保留到下一轮重试。
Binding 到期只产生可见的逻辑业务孤儿，不直接越过 Purpose 保留策略删除 Node、Version 或 Object。

### 23.6 实施顺序与待确认边界

1. 固化 Scope/Purpose/Binding 合同，不预注册延期功能的全局平台权限。
2. 增加 system space 与 `file_resource_bindings` 三方言迁移、约束、query 和并发/孤儿状态机测试。
3. 先迁移头像为 account scope 的逻辑 resource-managed 文件，证明旧引用与候选过期可无损迁移。
4. 提供业务模块上传/绑定/解绑窄能力，加入架构门禁，阻止新增直接 Driver、磁盘或 S3 写入。
5. 做存量扫描和迁移报告；未知 owner/purpose 只报告和隔离，不自动塞入 system/tenant 根。
6. 通过三方言、race、执行计划、故障恢复、权限矩阵和真实浏览器验收后再逐业务模块迁移。

平台级全局逻辑/物理查看不在上述顺序内，待实际需要时再单独设计和排期。

当前阶段明确排除：把 Object owner 当逻辑授权、每业务模块再建存储表、
每 Entity/Department 建 bucket、按角色隐式切换 `/files` 语义、把未知存量文件粗暴归到 system，
仅依赖定时任务最终清理却允许长期无归属对象，以及任何全局文件管理 API/Web 页面。
