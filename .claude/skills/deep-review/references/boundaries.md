# 输入取值目录:边界值与恶意输入

按**数据类型**穷举取值,与业务无关 —— 只要字段是这个类型,这些取值就适用。

`deep-review`、`deep-audit` 和 `deep-test` 共用这一份。

> **这是取值素材,不是必报清单。** 用途有两个:证伪时挑探针输入,写不变量测试时挑遍历集合。
> 报告里只收拿得到证据的发现;把整张表抄进报告等于制造噪音。

**边界的定义**:`上点`(边界值本身)、`内点`(区间内任一值)、`离点`(边界外最接近的值)。
一个 `1–100` 的区间要取 **5 个值**:`0`、`1`、`50`、`100`、`101`。**两端都做,缺一不可。**

## 先登记字段,再挑取值

**顺序不能反。** 事后补登记一定会漏掉当时没想到的字段 —— 漏登记一个字段,它的所有取值就整批消失,而且没人看得出来。

登记时逐个查这些**容易漏的位置**:

- 弹窗、抽屉、二级页面里的输入(理由、备注、原因这类)
- 搜索与筛选条件(它们也是输入)
- 分页参数
- 隐藏字段与上游带入的参数
- 富文本、附件、多选组件
- **同一字段在多处出现的多个实例** —— 分别登记,因为各处的校验实现可能不同

登记时标注字段角色:`input`(可编辑提交)、`filter`(查询条件)、`display`(只读展示)、`system`(系统传入)。
**只对真实可控的入口挑输入取值** —— 给只读字段编造输入路径是纯噪音。

## 两组,核对方式不同

| 组 | 类型 | 怎么算 |
|:---|:---|:---|
| **字段级**(1–9) | 整数 / 小数金额 / 字符串 / 日期时间 / 布尔枚举 / 集合 / 分页 / 文件 / 区间对 | **每个字段各核对一遍** |
| **场景级**(10–12) | 并发时序 / 权限身份 / 网络环境 | **整个功能核对一遍**,不随字段数重复 |

分错组是最常见的错:把场景级按字段重复一遍会让核对表膨胀成一堆重复行;
反过来整体漏掉它们,最危险的三类就根本不在范围里 —— 实测中这三类恰恰漏得最多。

## 1. 整数

`min`、`min-1`、`min+1`、`max`、`max-1`、`max+1`;**`0`**(即使区间不含 0 —— 很多实现把 0 当"未填");
**负数**(即使业务上不可能为负);**空 / 未传字段**(`null` 与缺字段是两件事);
**类型上限溢出**(32 位/64 位边界及再 +1);**非整数**(`1.5`、`1.0` —— 后者常被误判为合法)。

按需:前导零(`007` 是否被当八进制)、正号、千分位(`1,000` —— 前端格式化后回传的常见事故)、
科学计数法、超长数字串(溢出/截断/报错)。

## 2. 小数与金额

整数部分与小数部分**各自的边界**;**精度上限与上限 +1 位**(定义两位小数就试三位:截断、四舍五入还是报错);
**累加误差**(`0.1 + 0.2` 类 —— 用二进制浮点存金额这条必挂);
**舍入方向**(`2.5` / `-2.5` / `0.005`);**最小货币单位及再小一位**。

按需:负零、超出安全整数范围的精度丢失。

> 金额字段先查存储类型:定点合格,二进制浮点直接判不合格。

## 3. 字符串

**长度必须明确按字符还是按字节计** —— 中文在 UTF-8 里占 3 字节,"限 50 字"和"限 50 字节"是两个需求;不明确就是需求缺口。

空串(区别于 null 与未传);单字符;**最大长度、max-1、max+1**;纯空格(是否被当空值);
首尾空格(是否 trim;trim 后是否重新校验长度);换行与制表符(单行输入粘贴多行);
全角字符(是否与半角等价);**大小写**(唯一性校验是否区分);中文/日文/阿拉伯文(含 RTL 显示);
**Emoji 与代理对**(4 字节字符,截断时会不会劈成半个变乱码)。

按需:中间连续空格是否折叠、Unicode 组合字符(`é` 的两种表示,长度与相等判断不同)、
零宽字符(绕过非空校验的常见手法)、NULL 字节(截断攻击)、同形异义字(西里尔 `а` 冒充拉丁 `a`,账号仿冒)。

## 4. 日期与时间

区间起止四点(起-1 / 起 / 止 / 止+1);起止相等;起止倒置(是否拦截);
**月末**(28/29/30/31,尤其 1 月 31 日加一个月);闰年 2/29 及非闰年输入 2/29;
跨天/跨月/跨年(`23:59:59` → `00:00:00`);**时区边界**(同一时刻在 UTC+14 与 UTC-12 分属两天);
**远期与极值**:`1970-01-01`(纪元起点)、**`2038-01-19`(32 位秒溢出)**、`2099-12-31`、
`9999-12-31`(常被当"永不过期"的哨兵)、以及纪元之前的日期;未来日期(出生日期填未来);
非法日期(`2 月 30 日`、`13 月`)。

**`2100-02-29` 单独试一次** —— 2100 能被 4 整除但不是闰年(整百年需能被 400 整除),
`year % 4 == 0` 这种朴素实现会认为它存在。2000 年是闰年,所以这个 bug 到 2100 才会现形,
写代码的人多半没验过。

按需:夏令时切换(不存在的时刻与重复的时刻)、格式变体。

> 判据:**接口与存储统一 UTC,展示按客户端时区**。任何"存本地时间"的实现在跨时区场景必错。

### 存储范围是独立的一项,不要和输入校验混为一谈

**应用层收下了,不等于存得进去。** 时间列的上限由**列类型**决定,而不同数据库同名类型的范围可以差几千年:

| 类型 | 范围 | 后果 |
|:---|:---|:---|
| 32 位纪元秒(`INT` 存 unix time、部分 C 时间 API) | 到 **2038-01-19** | 溢出后回绕成 1901 年 |
| MySQL `TIMESTAMP` | 1970-01-01 ~ **2038-01-19** | **存 2099 会被拒绝或截断** |
| MySQL `DATETIME` | 1000-01-01 ~ 9999-12-31 | 安全 |
| PostgreSQL `TIMESTAMP(TZ)` | 公元前 4713 ~ 294276 年 | 安全 |
| SQLite(文本/数值) | 取决于写入方式与驱动 | 存纪元秒时同样受 32 位约束 |

**多方言项目必须逐列核对**:同一张表在 PostgreSQL 上用 `TIMESTAMPTZ`、在 MySQL 上用 `TIMESTAMP`,
业务写入 2099 时只有 MySQL 那侧失败 —— 而如果验证只用当前附近的日期,两侧都绿。

**这类值在真实业务里很常见**:长期有效期、终身授权、保修与合同到期、
以及用 `9999-12-31` 当"永不过期"的哨兵。**取值目录里的远期日期必须真的写进库再读回来比对**,
只在应用层构造一个 `time.Time` 断言不了任何存储层的事。

## 5. 布尔与枚举

所有有效值逐个;无效值/未定义值;`null` / 未传;空串。
按需:大小写变体、数字形式(`1`/`0`/`-1`)、**枚举扩容后的向后兼容**(与 `failure-patterns.md` A7 叠加)。

## 6. 集合与数组

空数组(区别于 null);单元素;最大元素数与 max+1;重复元素(是否去重);含 null 元素;超大集合(性能与超时)。
按需:元素顺序是否影响结果、嵌套深度(深层嵌套的解析栈溢出)。

## 7. 分页

第 1 页;末页;**末页 +1**(返回空列表还是报错);第 0 页与负页码;非整数页码;
每页 0 条与负数;**每页超大**(是否有上限保护,防拖库);**总数为 0 时的末页**(容易除零或算出第 0 页);
**深翻页**(响应时间是否随页码塌陷)。
按需:翻页期间数据变动导致的重复或漏读。

## 8. 文件

0 字节;1 字节;**大小上限与上限 +1(用真实大小的文件,不是小样本)**;文件名长度上限;
无扩展名;多重扩展名(`a.jpg.exe`);扩展名大小写;**扩展名与实际类型不符**(是否只看扩展名);
文件名特殊字符(空格、中文、emoji、`../`、`%00`);同名重复上传(覆盖/改名/拒绝);
**上传中断**(断网、取消 —— 是否留下半成品)。

## 9. 区间对(起止成对的字段)

只填起;只填止;两者都空;起 = 止;**起 > 止**;起止都超界;跨度为 0 与为最大。

## 10. 并发与时序（场景级）

同一操作重复提交(双击、网络重试 —— 是否幂等);并发修改同一条数据(后写覆盖还是冲突);
**并发插入相同唯一键**(应被唯一索引拦截并返回可读错误,不是 500);操作顺序颠倒(B 依赖 A 但 B 先到)。
按需:超时后的迟到响应、长事务与锁等待。

## 11. 权限与身份（场景级）

未登录访问;登录但无该功能权限;**有权限但访问他人/他方的数据 ID**;凭证过期/失效/伪造;
权限变更后旧会话是否立即失效;退出后的残留(缓存、推送、返回键)。

## 12. 网络与环境（场景级）

断网;弱网/高延迟;请求超时;**请求发出后断网(结果未知)**;服务端 5xx / 4xx;响应体为空或格式错误。
按需:响应慢于调用方超时设置。

## 恶意输入:六类刚性底线

**反向输入面不在需求文档里。** 需求会写"用户名 2–20 位",不会写"输入 emoji 会怎样"。
照需求设计验证,就会系统性地漏掉整个反向面 —— 所以这一组只能靠固定清单兜底,不能靠临场想。

每个真实可控的文本入口,以下六类缺任意一类即不合格:

| 类别 | 取值 | 验什么 |
|:---|:---|:---|
| **① 表情与组合字符** | `😀🔥` + ZWJ 序列 + 旗帜 | 存储、截断、长度计算、显示 |
| **② 业务特殊符号** | `%` `&` `"` `'` `<` `>` `#` `@` `\` `/` `\|` `:`,以及 `"10% discount"` `A & B` `it's` `a\|b` | **功能正确性** —— 真实用户会输入这些,不能因此存错或渲染崩 |
| **③ 格式化字符串** | `%s%s%s` `%d` `%n` `%x` `%p` | **必须独立于 ②** |
| **④ 脚本注入** | `<script>` `onerror=` `javascript:` 及实体编码绕过 | 原样保存或拒绝,不得被渲染执行 |
| **⑤ SQL / 命令 / 路径注入** | `' OR '1'='1' --`、`; ls`、`../../etc/passwd` | 不产生实际注入效果 |
| **⑥ NoSQL / CRLF / 模板注入** | `{"$ne":null}`、`%0d%0aX-Test:injected`、`{{7*7}}` | 对象查询、响应头与日志、模板链路 |

**③ 为什么必须独立于 ②**:`10% discount` 验的是业务文案能否正确保存展示;
`%s%s%s` 验的是后端格式化函数会不会把用户输入当格式串解析(某些语言里 `%n` 可写内存)。
测试目的、预期结果、失败后果完全不同,合并会让其中一个失去意义 —— **这是核对时最高频的误判点。**

按需追加:全角半角混用、混合内容(`10% off ❤️🔥` —— 真实输入通常是混合的,单字符验不出组合问题)。

## 覆盖判据:逐项核对,不用百分比

**判据是「每一项都有交代」,不是「达到某个百分比」。** 每一项要么指到一个具体的验证,要么写出**可被反驳的**豁免理由;
没有第三种状态,也不允许空着。

### 为什么不用百分比

百分比在三个层面制造问题:

1. **它奖励"报出一个数字",不奖励"逐条核对过"。** 凭印象也能报出一个数字,而且看起来和认真核对过的完全一样。
2. **它给注水留了空间。** 两种典型手法:把十几个场景塞进一条验证,于是"20/20 = 100%"在技术上成立,实际只有一条可判定;
   或者写"步骤同上,换个字段",计数好看但不可独立执行。
3. **分母由被考核方自己提供,而复核成本约等于重做。** 这个防线在经济上不成立,实践中必然退化成抽查。

逐项核对没有这些问题:**漏了就是漏了,表格里那一行是空的,一眼看得出来。** 不需要任何人做算术,也没有可以注水的靶子。

### 三种失效方式(自查与复核都用)

| 失效方式 | 表现 | 怎么查 |
|:---|:---|:---|
| **字段漏登记** | 有 8 个字段,登记表只列了 5 个 | 拿契约/接口/原型的字段清单逐一对照,重点查弹窗、搜索栏、分页参数、同名字段的多个实例 |
| **类型定错** | 金额登记成"整数",绕过小数精度整组 | 逐字段核对归类;**金额记成整数、日期记成字符串**最常见 |
| **理由不可反驳** | 大批项写"不适用""这个字段简单" | 见下;不合格的理由等同于未覆盖 |

### 豁免理由的写法

不接受"不适用"三个字,要写清**为什么**这个取值在这个字段上不成立:

- ✅ 「该字段为系统生成的标识,不可输入,故全角/大小写/首尾空格三项不适用」
- ❌ 「不适用」
- ❌ 「该字段简单」

区别在于前者**可被反驳** —— 复核发现该字段其实可编辑,豁免立刻失效。后者无法反驳,等于没写。

### 四类不接受豁免

判据仍然是**不可逆性**:

| 类别 | 为什么不能豁免 |
|:---|:---|
| 小数与金额(2) | 数值错误,而且已经被使用过 |
| 文件(8) | 数据丢失或安全缺口 |
| 并发与时序(10) | 重复副作用、脏数据 |
| 权限与身份(11) | 越权泄漏不可逆 |

其余各节可以写理由豁免 —— 它们的失效后果(显示异常、校验偏松)能在下个版本修掉。
