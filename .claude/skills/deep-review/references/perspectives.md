# 视角 brief

`deep-review`、`deep-audit` 和 `deep-test` 共用这一份。派 subagent 时把对应那一节抄给它。

配套的三份素材(都是线索与取值来源,不是必报清单):
`failure-patterns.md` 整条路径的失效模式、`boundaries.md` 单字段取值与恶意输入、`test-design.md` 怎么设计验证。
每节的"不找什么"和"不找什么"一样重要 —— 它是防止凑数的闸门。

**给每个视角的通用要求(都要带上):**
- 每条发现给出 `文件:行` 和一个能触发它的具体输入或场景。给不出证据就不要报。
- "这次改动与我的视角无关"是完整答案,直接回"无发现"。凑数比漏报伤害大。
- 只报告,不改代码。

---

## 并发与正确性
**触发**:写库、锁、goroutine、channel、事务、重试、租约、幂等、原子序列。
**找**:未检查的写结果(RowsAffected / 影响行数被丢弃)、本应原子的多步操作、TOCTOU、锁失效后继续执行、竞态下的重复分配。
**不找**:单线程逻辑的风格问题。
**已见实例**:INSERT 后用 UPDATE 补租期却丢弃 `RowsAffected`,锁过期时两个进程拿到同一个 worker id。

## SQL 与 NULL 语义
**触发**:SQL、ORM、查询构建器、谓词拼装、可空列、迁移;**项目支持多种数据库方言时,任何 SQL 或 DDL 改动都触发**。
**找**:三值逻辑漏洞(否定谓词在可空列上排除 NULL,与正向谓词不构成划分)、拼接出的恒真/恒假条件、`IN ()` / `LIKE '%%'` 这类"看起来在过滤实际没过滤"、索引失效、注入、**方言语义差异**(同一条语句在不同数据库上行为不同)。
**证据要求**:**渲染出真实 SQL,或建三行(有值/空串/NULL)跑一遍。** 内存里检查表达式看起来永远是对的,三值逻辑只有数据库会暴露。
涉及方言差异的发现**必须在真实目标数据库上复现**,不能用内存实现顶替 —— 内存实现恰好不复现这类差异。
**业务唯一键必须落在唯一索引上**,不能只靠应用层"先查再插";并发或重复插入要被约束拦截并返回可读错误,而不是 500 或静默产生重复行。
**时间列的取值范围由列类型决定,且各方言不同** —— 同名类型可以差几千年(见 `boundaries.md` 的存储范围表)。
新增或修改时间列时核对:业务上可能出现的最远日期(长期有效期、`9999-12-31` 这类"永不过期"哨兵)
在**每个**方言上都存得进去;用 32 位纪元秒存时间的一律按 2038 上限对待。
只用当前附近的日期验证时,这类缺陷在所有方言上都是绿的。
**已见实例**:`col <> ''` 与 `col = ''` 都排除 NULL 行;`Eq(nil)` 渲染成 `IS NULL`,`Neq(nil)` 渲染成 `IS NOT NULL` 静默匹配全表。
**已见实例(方言差异,单引擎测不出来)**:MySQL 把 `22junk` 宽松转成 `BIGINT` 22,越权查询因此命中;MySQL 对未改变值的
UPDATE 返回 `RowsAffected=0`,被误判成"目标不存在";PostgreSQL `CHAR(64)` 给空 hash 补空格,链式校验失配;
MySQL 保留字撞上表别名;binary collation 下大小写不同的恢复查询查不到人;
时间列一侧用 MySQL `TIMESTAMP`(上限 2038)另一侧用 `TIMESTAMPTZ`(上限五位数年份),写入远期日期时只有一侧失败。

## 数值与精度
**触发**:金额、计费、分摊、税费、折扣、退款、汇率、单位换算,以及任何会被累加或反向还原的数值。
**找**:用二进制浮点存金额(见到直接判不合格,不必再往下看)、舍入方向未定义、分摊余数无归属、
计算顺序影响结果(先折后税与先税后折不同)、累加后反向汇总还原不回去、多币种的汇率取值时点与精度。
**证据要求**:给出一组具体输入和你**独立算出**的期望值。拿实现的输出当期望等于没验。
**为什么必须单独看**:偏差以极小的量持续产生,单笔看不出来,累积到对账才暴露 —— 而那时数值已经被使用过很多次,不可逆。
**不找**:没有明确公式契约时,凭字段名叫"合计""余额""税额"就断言算错 —— 那是需求缺口,按缺口报,不按发现报。

## 契约与兼容
**触发**:HTTP/gRPC/proto/OpenAPI 变更、wire 类型、序列化、版本化字段。
**找**:破坏性变更、生成的文档与实际接受的参数不符、序列化不能往返(marshal 出来的值 unmarshal 不回去)、同一语义在不同接口上表示不一致。
**已见实例**:注释声称过滤器已写入 OpenAPI,实际 `Operation.Parameters` 从未被设置;`MarshalJSON` 输出 null 而 `MarshalText` 输出 "0",而 `Parse` 拒绝 "0"。

## 存量数据与版本兼容
**触发**:已运行过一段时间的系统上的规则变更、字段增删、枚举扩容、默认值调整、schema 迁移、灰度期间新旧版本并存。
**找**:新代码遇到按旧规则创建的数据 —— 旧记录缺字段、旧枚举值不在新的取值集合里、旧格式解析失败、
新增必填字段后旧记录为空时的读改删导出、规则放宽或收紧后越界的历史数据能否展示与修改、
同一条数据被新旧两个版本先后写入。
**为什么会被系统性漏掉**:**测试数据都是新造的** —— 按当前代码、当前规则创建,所以旧数据路径在测试环境里天然不存在。
这不是"想到了但没测",是这条路径在那里根本不会出现,直到线上遇到真实老数据。
**证据要求**:用**变更前的格式**造一批记录,再用新代码读、改、删、导出。只读代码判断兼容性不算证据。
**不找**:对从未上线过的新表谈存量兼容。

## Swagger/OpenAPI 接口规范
**触发**:HTTP 路由、handler、请求/响应类型、接口注解、OpenAPI 生成器或规范文件变更；`deep-audit` 审计任何提供 HTTP API 的范围时必选。
**先读**:`openapi.md`，并以实际生成的规范为输入，不能只读源码声明。
**找**:路径不是稳定资源、层级或命名风格分裂；path/query/header/body 参数放错位置或名称/类型/required/default/nullable 与运行时不一致；HTTP 方法、幂等性、状态码、分页/过滤/排序、错误 schema、operationId/tag/security 在同类接口间不统一；规范漏路由、幽灵路由或破坏兼容性。
**证据要求**:每条给出 `METHOD /path`、生成规范位置、运行时路由或同类 operation 对照、违反的项目约定或行业标准及实际影响。能执行时用真实请求确认规范与实现差异。
**不找**:没有项目约定和实际影响的个人审美；为了“更 REST”而重命名已经稳定发布且无迁移方案的接口。

## 架构与耦合
**触发**:新模块、新依赖方向、新抽象、跨层引用。
**找**:依赖方向倒置、循环依赖、单实现的接口、为一个用例造的框架、绕过既有扩展点另起一套。
**不找**:"可以引入 X 模式"。设计模式是命名问题的词汇,不是清单。只有当代码**已经在手写某个模式的劣化版本**,或**缺少某个原则导致了具体可复现的问题**时才提。
**已见实例**:同一个"init 需要数据库"的问题,仓库已有两种既定处理(快速失败 / 按操作解析),新代码引入了第三种。

## 复用与重复
**触发**:任何改动。
**找**:新写的东西仓库里已有、同一逻辑第二次实现、为同一问题引入平行的第二套模式。
**做法**:动手改之前先 grep 关键名词。这条视角靠搜索,不靠读。

## 安全
**触发**:输入解析、认证、鉴权、密钥、外部调用、文件路径、模板渲染、反序列化。
**找**:注入、越权、信息泄漏(错误信息回显用户输入、日志打印凭据)、不安全默认值、未校验就拼进 DDL/命令/路径的标识符。

**越权分四类,别混着谈**:跨租户(A 租户拿到 B 的数据)、水平(同租户内访问同级他人数据)、
垂直(低权限角色调用高权限接口)、未授权(无 token / 过期 / 伪造)。**跨租户优先级最高** —— 一次泄露就够毁掉整个多租户系统的信任。

**权限的单位是接口,不是页面。** 前端隐藏入口只是体验,服务端不拦就是漏洞;一律用接口直接验证。
**最常被漏掉的三个入口:下拉数据源 / 联想搜索、导出、附件下载** —— 它们通常绕过了主流程的权限校验。
导出、打印、分享链接、消息通知、报表汇总这些**旁路**要和主列表受同一套约束。

**两条容易漏的判据**:
- **响应不可区分** —— "存在但无权"与"根本不存在"必须返回同状态码、同文案、同量级响应时间,否则可被用来枚举 ID。
- **写接口要回查** —— 返回 403 不代表没写进去,必须回查目标数据确实未变。批量接口混入他方 ID 应整体拒绝,不得部分执行。

**客户端传来的身份标识一律不可信**:body/header/query 里的 `tenantId`/`ownerId`/`createBy` 之类,服务端必须以会话身份为准。

**反向输入面不在需求文档里**,只能靠固定的一组兜底:emoji 与组合字符、业务特殊符号(`%` `&` 引号 `<>` `|`)、
格式化串(`%s` `%n` —— 与业务文案里的 `10%` 是两回事,不能合并)、脚本注入、SQL/命令/路径注入、
NoSQL/CRLF/模板注入。改动触及可控文本入口时按这一组核对。

**不找**:泛泛的"建议加强安全性";对只读字段编造输入路径。

## 性能与资源
**触发**:循环内查询、大对象、缓存、连接池、批处理、新增或改写的查询与索引。
**找**:N+1、无界增长(队列/切片/map 没有上限)、未关闭的资源、锁竞争、本可一次完成的重复查询、
**数据量上去才会痛的查询**(全表扫描、写了索引但用不上、缺少租户/作用域谓词、排序分页落到临时表)。
**证据要求**:说清数量级怎么来的 —— "N 是什么"。
**项目有 EXPLAIN 基线或性能门禁目标时,必须跑它取证**(即冻结了执行计划与阈值的那个门禁目标),
拿实际执行计划说话;没有基线才退回数量级推理,并在报告里写明这是推理不是实测。
**没有阈值的性能结论不算结论。** "加载流畅""响应快"等于没测。每条要带:数据量、并发、指标、阈值、判定方式;
**取 P95 不取平均值**(平均值会被大量快请求掩盖长尾)。项目没有 SLA 时按下面这组通用口径判定,
**同时把"需求未定义性能指标"作为缺口报出来** —— 不要自己编一个阈值当成需求。

通用口径(需求另有规定时以需求为准):慢查询 > 500ms 即不合格;禁止全表扫描与 N+1(列表 N 行不得产生 N 次查询);
深翻页不得随页码线性劣化;单次查询必须有返回条数上限,不允许一次拉全表;
汇总/导出超过十秒量级的必须转异步,不得阻塞请求;长时间运行下内存与连接不得持续单调上升。

**不找**:没有数量级论证、也没有执行计划支撑的"这里可能会慢"。

## 依赖健康
**触发**:go.mod / package.json / lock 文件变更。
**找**:新依赖是否已有替代、版本是否停维护、许可证、传递依赖污染、能否几行代码自己实现。
**不找**:与本次改动无关的存量依赖(那是 deep-audit 的活)。

## 可测性与覆盖
**触发**:任何改动。
**找**:**名不副实的不变量测试** —— 名字叫"X 必须等于 Y"却只断言了非空;断言证明不了需求;测试跟着实现改而不是反过来;缺失的失败路径与边界。
**已见实例**:一个叫 `TestDescribeMatchesWhatParseAccepts` 的测试只断言了算子名非空,从没真的拿它们 parse 过 —— 于是"描述即解析"这条不变量长期形同虚设。

## 运维与可观测
**触发**:降级路径、重试、失败分支、一次性初始化。
**找**:静默降级(错误被吞、没有日志)、无法诊断的失败、一次性计算依赖运行期可变状态、告警缺少可操作信息。
**面向用户的失败必须可操作**:有明确提示、能定位到具体字段、网络类异常给得出重试路径,
且**不得把堆栈、SQL、内部错误码泄漏给终端用户**。
**告警本身也要验**——它只在别的东西坏掉时才起作用,因此是最容易长期失效而无人察觉的一环。
**已见实例**:注册路由时数据库不可用则跳过文档生成,错误被吞掉,症状要到生成的客户端不能过滤时才显现。

## 产品闭环
**触发**:用户可见行为变更、状态机、多步骤流程。
**找**:功能是否闭环(能进不能出、能建不能删、能失败不能重试)、错误信息是否可操作、边界状态(空、首次、并发编辑)有没有归宿。
**提示与实际副作用必须一致** —— 报"发送成功"而实际没发出去,是最容易漏且后果最重的一类,因为界面看起来完全正常。
**状态机要查中断路径**:正向流程通常测得很足,但状态常在"进入下一步"时就被提前写入;中途退出后对象停在一个
没有恢复入口的中间态,当事人被永久卡住,只能改数据解开。逐个节点问:在这里退出再进来,状态和界面还自洽吗?
**不找**:需求本身该不该做 —— 那不是评审能决定的。

## 命名与注释一致性
**触发**:任何改动。**这条视角便宜且命中率极高,永远要派。**
**找**:**注释宣称的行为与代码实际行为不符**、名字与行为不符、目录/文件/结构体/字段用词语义模糊或与内容不符、文档说"已处理"而代码没处理。
**做法**:逐条读改动里的注释,对着代码问"这句话是真的吗"。
**已见实例**:一轮自查抓出四处注释与代码不符,其中一处宣称一个守卫覆盖了某种输入,实际只覆盖了字面空值。

## 跨平台
**触发**:文件路径、换行、时区、大小写敏感、文件权限、系统调用、临时目录。
**找**:硬编码分隔符、依赖大小写不敏感的文件系统、本地时区假设、只在一种 libc 上成立的行为。

## 事务与分布式
**触发**:多表写、跨服务调用、消息、锁、幂等键、补偿、本地暂存后批量提交、大批量写入。
**找**:事务边界不覆盖必须原子的部分、跨服务调用放在事务里、重试没有幂等保护、补偿路径本身会失败、
时钟假设(用本地时钟判断远端租约)、**没有事务保护的窗口**(数据先落在一侧、稍后再批量提交到另一侧,
窗口内任何失败都可能让已完成的工作永久消失,且当事人无法重做)。
**幂等的判据是副作用只发生一次**,而且**冲突时要返回与首次一致的结果,不是报错** —— 报错会让调用方以为失败再试一次。
覆盖:重复提交、网络重试与超时重发、回调重放、消息重复消费、调度器重复触发;并确认幂等键的作用域和有效期。
**已见实例**:分布式锁的续租依赖进程本地单调时钟,而过期由数据库时钟裁决 —— 这个组合是对的,但需要写明假设。
