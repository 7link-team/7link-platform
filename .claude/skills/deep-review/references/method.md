# 方法学:证据、归类、不变量测试、CI

`deep-review` 和 `deep-audit` 共用这一份。

## 证据门槛

一条发现要进报告,必须有人能照着复现。按强度排:

1. **临时探针测试** —— 写一个 `zz_probe_test.go`,跑,贴输出,删掉。最强的证据,尤其是 SQL 三值逻辑、并发交错、序列化往返这类"读代码看不出来"的东西。
2. **渲染真实产物** —— 打印出实际的 SQL、生成的 OpenAPI、marshal 结果。
3. **源码调用链** —— 确认这个分支真的可达,谁调用它,传什么。
4. **`git show` 前后对比** —— 判断是不是回归。

达不到这四条中任何一条的,不是发现,是建议 —— 放到报告最后的"建议"节,最多 5 条。

**探针测试用完就删。** 它是证据,不是要留下的测试;要留下的是阶段 6 的不变量测试。

## 归类与扫类

这是让评审收敛的那一步。

对每条为真的发现,往上抽一层:

> 这条的**成因**是什么?这个成因还能在哪里产生同样的后果?

抽出来的应该是一句可以拿去搜索的话,比如:

- "解析函数返回了零值加 nil 错误,而调用方只检查错误" → grep `return nil, nil`,以及所有接受"调用方提供的解析函数"的地方
- "检查跑在归一化之前,归一化之后又变空了" → 找所有先校验后转换的路径
- "两个从同一份声明派生的产物互相不一致" → 找所有 declaration-driven 的成对产物
- "一次性计算依赖运行期可变状态" → grep 初始化/注册阶段读取运行期资源的地方

然后**真的去扫**,把找到的其它实例一并列进报告的"类扫描"节,写清楚全仓有几个实例、分别在哪。

只报一个实例、不做扫类,就是在保证下一轮还有新发现。

## 不变量测试

每个被修掉的类留下一个测试,而且要**对集合做全称断言**,不要只钉住这一个实例。

区别:

```
钉实例:  断言 isEmpty:false 在这个字段上返回了正确的行
钉类:    对每一组"问题 + 反问题",断言 结果集并集 = 全表 且 互斥
```

后者能自动覆盖以后新加的算子;前者只能覆盖今天这一个。

写不变量测试时:

- **跑真实产物**。三值逻辑、序列化往返、SQL 语义,在内存里检查表达式永远看起来是对的。
- **遍历集合而不是枚举用例** —— 遍历所有算子、所有字段类型、所有已注册路由。新成员自动进入覆盖,不需要有人记得补。
- **名字要说清断言什么**,并在注释里写明它防的是哪一类回归,以及**当初为什么没被抓住**。

**已封类的账本就是这些测试本身,不要另建文件记录。** 项目通常已经限制了状态文件数量,再加一个只会腐烂。

## 变异验证(不做等于没做)

新写的每个不变量测试都要验证它真的会失败:

1. **先备份文件**(`cp file /tmp/bak`)
2. 把修复改坏
3. 跑那个测试,**必须失败**
4. **从备份还原**

### 严重的坑

**不要用 `git checkout -- <file>` 还原。** 它还原到 HEAD,会把你这次的修复一起抹掉,而不是只撤销变异。用文件备份。

批量验证时用备份的写法:

```bash
BK=/tmp/mutbk && mkdir -p $BK

# mut 文件 旧串 新串 测试包 测试名 标签
mut() {
  cp "$1" "$BK/$(basename $1).bak"
  OLD="$2" NEW="$3" python3 -c 'import os,sys
p=sys.argv[1]; s=open(p).read()
assert os.environ["OLD"] in s, "变异串没匹配上"
open(p,"w").write(s.replace(os.environ["OLD"], os.environ["NEW"], 1))' "$1"
  if go test "$4" -run "$5" >/dev/null 2>&1; then
    echo "X  非回归测试(去掉修复仍然通过): $6"
  else
    echo "OK 去掉修复即失败: $6"
  fi
  cp "$BK/$(basename $1).bak" "$1"   # 从备份还原,绝不用 git checkout
}
```

如果变异后测试仍然通过,那个测试没有在测你以为它在测的东西 —— 重写它,不要放过。

## CI 门禁

跑**项目自己的 CI 目标**,不是你自己拼的命令。`go build && go test` 会漏掉 lint、格式检查、覆盖率下限、集成测试。

探测顺序:

1. `Makefile` 里的 `ci` / `check` / `verify` / `all` 目标(`grep -nE '^(ci|check|verify|lint|test):' Makefile`)
2. `package.json` 的 `scripts.ci` / `scripts.check`
3. `.github/workflows/*.yml` 里实际跑的命令
4. `justfile` / `Taskfile.yml` / `noxfile.py` / `tox.ini`
5. 都没有时,退回到语言默认(`go build ./... && go vet ./... && go test ./...`),并在报告里**说明项目没有 CI 目标**

注意 CI 目标可能在子目录(比如 `apps/backend-api/Makefile`)。

**跑完贴关键输出。** 说"CI 通过"必须真跑过并给出证据 —— lint 的沉默、覆盖率的数字、集成测试的行。

## 写注释的一条纪律

修复时写下的每一句注释,写完再读一遍问:**这句话现在是真的吗?**

这次会话里,一轮自查抓出四处注释与代码不符,其中一处是"为了准确性而修改过的注释"仍然在过度宣称。注释比代码更容易腐烂,因为编译器不检查它。
