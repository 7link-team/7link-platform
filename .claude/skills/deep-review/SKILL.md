# 深度评审

## 这个 skill 存在的理由

普通评审的失败模式是**一轮一轮出新问题**:每轮修掉被指出的那一处,下一轮从同一个成因里冒出另一处。

原因是修实例不修类。这个 skill 的全部结构都是为了让评审收敛:

1. 每条发现必须**先证伪**才能进报告 —— 跑一次、渲染一次、复现一次
2. 每条发现必须**归类**,然后沿着这个类**扫全仓**
3. 每个被修掉的类必须留下一个**对集合做全称断言**的测试
4. 最后过**项目自己的 CI**,不是 `go build && go test`

省掉任何一步,下一轮就会有新发现。

## 反 checklist 约束(最重要的一条)

"覆盖所有视角"最容易退化成一张巨型清单,产出几十条泛泛而谈的建议 —— "这里可以考虑引入策略模式"、"建议增强可观测性"。那种报告的信噪比比没有还差,用户会开始跳过它。

所以:

- **视角交白卷是完整答案。** 派出去的每个视角都必须被明确告知:这次改动跟你无关就说"无发现",不要为了交差凑。凑出来的发现比漏掉的发现伤害更大。
- **设计原则和设计模式是命名问题的词汇,不是要满足的清单。** 只有当现有代码**已经在手写某个模式的劣化版本**,或者**缺少某个原则导致了一个具体可复现的问题**时才提。不得因为"可以引入 X 模式"而提。
- **没有证据的不是发现,是建议。** 建议单独成节,最多 5 条,排在报告最后。

## 调用

```
/deep-review          默认:改动为入口,按改动自动选视角
/deep-review all      强制全视角(改动跨度大、或不放心自动选择时)
```

没有别的参数。全仓审计用 `deep-audit`;检验现有测试抓不抓得住回归、补门禁用 `deep-test`。

## 流程

### 阶段 1 — 定范围,选视角

确定评审目标,按优先级:

1. 用户明说的目标(某个 PR、分支、路径)
2. `git diff @{upstream}...HEAD` —— 未推送的提交
3. 工作区改动 `git diff HEAD`
4. 都为空时:最近一次提交 `git diff HEAD~1..HEAD`,并说明你在评审什么

拿到 diff 后读 `references/perspectives.md`,按每个视角的**触发条件**判断该派谁。默认模式只派触发的;`all` 模式全派。

只要范围内存在 HTTP 路由、handler、请求/响应类型、接口注解、OpenAPI 生成器或规范文件改动，
**必须**同时读 `references/openapi.md` 并派出“Swagger/OpenAPI 接口规范”视角；不能因为 CI 能生成文档就跳过接口设计评审。

视角是从改动**正向**推导的。再做一次**反向核对**:读 `references/failure-patterns.md` 的 A 类八条,
逐条问"这次改动会不会撞上"。这八条的共同点是**失效不可逆**,且**通常不在需求和 diff 的字面里** ——
正向读 diff 读不出"这条路径整体失效"。**判定为不触及也要留痕**,否则读者分不清"评估过认为无关"和"根本没想到"。

在报告里列出**派了谁、跳过了谁、为什么跳过**,以及 A 类八条的比对结论 —— 让用户能看出覆盖面,而不是猜。

### 阶段 2 — 并行扫描

每个视角派一个 subagent,**上下文隔离**:只给它 diff、它自己那份 brief、以及它需要自己去读的文件路径,不要把整个会话历史塞进去。

给每个 subagent 的指令必须包含:

- 它的视角 brief(从 `references/perspectives.md` 抄给它)
- **证据要求**:每条发现要给出 `文件:行` + 一个能触发它的具体输入或场景。给不出就不要报。
- **允许交白卷**:"这次改动与你的视角无关"是完整且有价值的回答。
- **不要修代码**:只报告。

多个视角在同一条消息里并行发出。

### 阶段 3 — 证伪(主 agent 亲自做,不外包)

subagent 会报错东西。这次不是走过场:

**每条发现必须亲自验证后才能进报告。** 手段按可用性排:

- 写一个临时探针测试跑一遍(最强,SQL 三值逻辑这类只有数据库会暴露)。
  挑输入取值时用 `references/boundaries.md`,别只试"看起来正常"的那个值
- 渲染出真实产物(SQL 语句、生成的 OpenAPI、序列化结果)
- 读源码确认调用链和实际语义
- `git show` 对比改动前后,确认是不是回归

验证后给出判定,只有三种:

- **真** —— 有具体输入能触发
- **假** —— 设计如此,附上写明这一点的注释、测试或文档位置
- **误诊** —— 现象存在但成因或方向说反了,给出正确的那个

判"真"的还要标**可达性**(见报告格式)。这比"严重/高/中/低"有用得多。

### 阶段 4 — 归类,扫同类

**这是收敛的关键一步,不要跳过。**

每条为真的发现,往上抽一层问:**这是哪一类缺陷?** 然后拿这个类去全仓扫其它实例。

做法见 `references/method.md` 的"归类与扫类"。

### Swagger/OpenAPI 接口门禁

当评审范围触发 HTTP/OpenAPI 视角时，按 `references/openapi.md` 执行。必须生成或获取**实际最终规范**，
对全部受影响 operation 建立 method/path/operationId/参数/请求体/响应/security 清单，并与运行时路由和同类接口对照。
至少明确回答：路径风格是否统一且表达资源关系，参数位置、命名、类型、required/default/nullable 是否合理，
HTTP 方法与状态码是否符合语义，分页/过滤/排序/错误响应是否复用统一契约，以及是否产生破坏性变更。

只读注解或 handler 不算完成；生成规范与运行时不一致时，必须用真实请求或路由注册结果确认哪一侧错误。
报告中的每条接口发现都要给出 `METHOD /path`、对应规范位置、违反的项目约定或通行标准及实际影响。

### 阶段 5 — 报告,等确认

按下面的格式出报告,然后**停下等用户点头**。不要自动进入修复。

### 阶段 6 — 按类修复

用户确认后,按类修 —— 不是按报告里的条目修。每个类修完补一个不变量测试,并做**变异验证**(把修复改坏,确认测试失败,再还原)。

做法和坑见 `references/method.md`。

### 阶段 7 — CI 门禁

跑**项目自己的 CI 目标**,不是 `go build && go test`。探测方法见 `references/method.md`。

**门禁通常不止一个。** 找到 `ci` 目标不等于找全了 —— 真实数据库、性能基线、生成物幂等这类慢门禁经常拆在 `ci` 之外。
枚举全部验证目标,相关的全跑;跑完核对冻结产物(生成物指纹、schema 锁、契约基线)没有漂移。**漏跑等于没跑。**

跑通后停在提交前,汇报跑了哪些目标、跳过哪些及理由。除非用户明说,不要自动提交或推送。

## 报告格式

```markdown
## 评审范围
[评审了什么 diff / 多少文件]
派出视角:A、B、C
跳过:D(无 SQL 改动)、E(无依赖变更)

## 发现

### 现网可触发
每条:判定 | 类 | 可逆性 | 文件:行 | 触发它的具体输入 | 影响 | 建议修法
**本节内部按不可逆的排在前面**,不按严重度词。

### 潜伏
代码路径存在但当前无调用者或无声明能到达。写明**为什么今天到不了**,以及什么改动会让它变得可达。

### 非缺陷
被报出但判定为假或误诊的,附证据位置。别省略这一节 —— 它是别人复核你的依据。

## 类扫描
每个类:类名 | 全仓实例数 | 分别在哪

## 建议(无证据,不属于发现)
最多 5 条。
```

**可达性比严重度有用。** "真但今天零实例"和"现网可触发"要分开放,用户据此排期。这次改动够不到的问题不该和线上正在发生的问题排在一起。

**同为现网可触发时,按不可逆性排序,不按频次也不按严重度词。** 判据只有一句:**失效之后能不能补救。**

- **不可逆** —— 数据丢了、越权方已经看到了、钱算错并已入账、重复扣款、审计链断了。修好代码消除不了已经发生的损失。
- **可逆** —— 文案、排序、布局、提示不友好。下个版本修掉,期间忍一忍。

**不要用缺陷统计定优先级。** 统计有双向偏差:某类缺陷数量少,可能是它不容易错,也可能是**根本没测**——
没测到的不会进缺陷库;而在测得少的地方,唯一能被发现的是严重到瞒不住的那些,于是该领域的"致命率"又虚高。
不可逆性这个判据不依赖任何统计,也不会被样本偏差污染。

**"建议修法"要具体到能直接替换进去。** "建议完善错误处理"没有任何用 —— 对方已经知道它不完善,
不知道的是改成什么。给出可以照抄的那一版:改哪个函数、判断换成什么、缺的分支补什么。
缺失的测试同理,给出能直接落地的断言形态,而不是"建议补充测试覆盖"。

## 不要做的事

- 不要在阶段 5 之前修任何代码
- 不要把 subagent 的完整执行过程抄进报告,只要结论和证据
- 不要因为某个视角"没找到东西"就去凑一条
- 不要用严重度代替可达性
- 不要声称跑过没跑过的东西 —— 说"跑了 CI"就必须真跑了,并贴关键输出
