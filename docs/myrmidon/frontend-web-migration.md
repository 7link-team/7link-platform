# 原型转入生产 Web：切换方案与交付约定

日期：2026-10-15。状态：**已批准执行，基础能力迁移进行中**。用户已同意转入 `apps/frontend-web` 的方向；本文件把实施范围、交付层级和逐项验收方式具体化。按下列工作包逐项落地，当前尚未发布或删除原型；实际验证进度见配套清单。

配套：[逐项迁移与验收清单](frontend-web-migration-checklist.md)；需求权威为 [PRD_FINAL](../PRD_FINAL.md) 和 [REQUIREMENTS](../REQUIREMENTS.md)，原型证据为 [COVERAGE](../prototype/COVERAGE.md)。若冲突，以用户最新确认和需求正文为准，不能让旧截图、旧测试或本方案改变业务语义。

## 1. 结论与用户最终拿到什么

推荐停止在独立原型中继续建设通用表单、列表和应用框架，改为在现有 Web 工程逐模块交付。原型保留作为设计、业务流程和验收样本，不能整目录搬进生产，也不能删掉后再凭记忆重写。

### 1.1 本次方案交付

1. 本文：源码依据、目标架构、页面去向、依赖顺序、风险和切换机制。
2. 配套清单：实施工作包、页面/隐藏入口矩阵、423 个唯一 REQ 的全部条款行及 70 个场景、74 个现有原型浏览器脚本的迁移归属。
3. `MEMORY.md` 保存当前进度，`ADR.md` 保存已确认方向；之后只在这些已有位置维护续作状态，不新建任务状态体系。

### 1.2 实施后的交付形态

用户打开同一个 Web 应用，登录、租户/平台/个人身份、授权和文件能力继续使用真实生产实现。在授权租户范围进入协作工作空间，看到已确认的原型布局与业务流程：唯一项目选择器、任务列表/看板/日历同排操作、对象详情原位打开并支持独立地址、表单统一详情/编辑、文件与成果预览、完整的成功/失败/无权/冲突反馈。

交付代码位于 `apps/frontend-web`，共享组件来自 `packages/ui`，业务页面和数据接入留在 `apps/web`。任务、消息、工作流、执行、交付的业务状态由真实服务决定；页面不能通过改 localStorage 来冒充执行成功。

必须分别签收以下层级，不能只给一个“完成”勾：

| 层级 | 用户可得到什么 | 通过条件 | 不代表什么 |
|---|---|---|---|
| U：Web 交互迁移 | 在生产工程运行、复用组件的完整页面与流程；尚无接口的部分仅在显式开发/测试模式演示 | 页面、状态、导航、权限展示、响应式、语言、组件测试和浏览器用例通过 | 不代表数据库、调度、实时通信或外部执行完成 |
| S：真实服务接通 | 真账号/真授权/真接口/真持久化，重启或跨设备后事实一致 | API 契约、服务端负向用例、并发与端到端闭环通过 | 不代表生产规模、全平台、所有第三方 runtime 已验证 |
| R：发布验收 | 对声明支持的范围可部署、可回滚、可观测 | U+S、回归、故障恢复及对应性能/平台用例通过，未完成项不作为正式可用功能开放 | 不代表 423 条需求被截图或少量测试整体通过 |

**迁移总完成**：全部纳入页面的 U 验收通过，所有 S/R 条目各有明确归属与证据；如果 S/R 仍待做，必须称“交互迁移完成，生产闭环未完成”。**产品完整完成**：需求和场景账本所有适用层级通过。不能把后端依赖写成无归属的“以后接 API”。

### 1.3 原型已有价值如何保留

保留流程、字段含义、权限矩阵、状态转换、固定版本、异常恢复、视觉规范与测试意图。按模块改写类型与数据接入，测试断言保留业务含义。原型 store、模拟用户角色、假回执、hash 路由和全局 CSS 不作为生产基础直接复制。已有生产 IAM 同样纳入统一框架规范与排查，不因历史实现而豁免。文件浏览器、账户安全流程、导航树等保留适合其语义的交互，但仍遵守统一权限、字段、状态反馈与布局规范；不将专业交互强行改成数据表格。

### 1.4 多业务扩展约束（2026-10-15 补充）

后续不仅有协作/技术服务，也可能增加 B2B2C 商城和其他产品。详见 [多业务平台架构方案](../multi-product-architecture.md)：共用 IAM 身份与基础能力，产品业务/权限/数据归属分别维护；消费者应用可独立前端，后端先按现有模块机制扩展，实际需要时再拆服务。

新增 X00–X11 工作包不替换本方案 M00–M20。当前 M00/M01 先承接 X00/X01 的产品/应用/组织边界设计；未来消费者 SSO、业务 API audience、开通资格和跨应用退出分别是后续对应产品正式开放前的门禁。不能把 IAM 运营平台当产品目录，也不能把买家加入商家租户来绕过当前 OAuth 的成员准入。

### 3.1 必须随接入关闭的组件问题（初始发现与当前状态）

这些不是可无限后置的美化项，归入清单 M02/M03。以下为初始问题台账，不等于全部仍未修复：只读提交保护和只读值展示已有部分实现，见验收清单首批实施证据；生产接入与其余缺口仍须逐项验证：

- `use-auto-form.ts` 的 `handleSubmit` 没有详情模式写入阻断；`AutoForm readonly` 也不能只约束渲染。要覆盖按钮、Enter、外部 form submit、自定义 renderer，并确保不会触发写请求。
- `readonly-value.tsx` 的 `optionLabel` 按对象索引，不能正确普遍处理 options 数组；password 落入字符串展示分支；日期区间和金额单位需要按契约格式化。只读不能泄露秘密，也不能把 ID 或数组对象当展示值。
- `CrudForm` 加载失败设 null 后继续显示空表单；copy 模式提交分支需要验证为创建而不是编辑原对象。只有实际采用该组件的批次才修其接入相关路径，不顺带重写整个 CRUD 库。
- `AutoTable` hook 有 error，但组件未展示；`CommonTable` catch 置空列表/总数。错误必须不同于真实空数据，提供保留查询条件的重试。
- 列筛选、排序、分页、刷新、导出必须共享同一授权查询。原型的 JSON 导出、CommonTable 当前页 CSV、真实后台全量导出不是同一个承诺；迁移前按需求确定范围/格式并明确提示，不静默互换。
- 生产权限按钮不能依赖 CRUD 默认“可编辑/可删除”；详情可见、字段可见、操作可用和服务端授权分开校验。

## 4. 目标组织方式与路由

依赖方向：`apps/web 业务页面 → packages/ui 通用组件`；`apps/web 业务客户端 → 已有认证/作用域传输 → 服务`。UI 包不导入 apps/web 或 docs/prototype，业务页面也不直接依赖原型 store。不要增加第三套通用表单、列表、请求框架。

建议位置（新文件仅在具体批次确需时建立，不预创建空壳）：

- `apps/web/src/app/` 下按已有页面惯例放协作页面；业务对象详情主体由路由页面和原位面板复用。
- `apps/web/src/components/` 放仅本应用共享的对象面板、项目选择等。
- `apps/web/src/lib/` 放业务客户端、契约转换和现有权限接入；不把所有协作领域堆入一个新 store。
- `packages/ui/src/components/auto-form`、`auto-table` 等扩展通用能力；翻译写入现有消息目录。
- `apps/web/src/**` 的现有测试惯例和 `apps/web/tests/` 浏览器验收承载生产证据。

### 4.1 当前一期边界冻结（X00/X01）

用户已批准先做必要边界再逐功能落地。基于现有 `router.tsx`、`route-loaders.ts`、`app-sidebar.tsx`，当前一期采用：

- **身份**：沿用 IAM 全局主体与租户成员关系；项目负责人不是另一套账号。保留账户视角限制与现有授权加载机制。
- **业务归属**：协作项目属于明确 tenant；按 `specs/07-projects-delivery.md`，档案属于 delivery 模块，项目主键等于 core entity ID。不能用前端选择器创造授权，也不能把任意 entity 自动视为项目。
- **应用**：当前复用 apps/web；通用组件不读取项目/商城业务数据。未来消费者应用可以独立部署，共享包不强制共享管理台路由。
- **服务**：当前按模块单体接线，复用现有事务/模块生命周期；不新建空微服务、不提前改 OAuth 准入、不新增没有业务需求的产品注册表。
- **组织与产品**：运营平台仍是组织根，不改成产品目录。商城买家、商家、店铺关系及跨域 SSO 属于后续 X 包触发项。

这冻结当前迁移约束，不表示消费者 SSO、商城权益或项目后端已实现。

## 5. 详情、编辑与规则共用的具体落地

### 5.1 表单共用什么

同一业务字段配置提供名称、显示格式、类型、布局、编辑控件、关联选择和 UI 联动。add/edit/detail/copy 使用模式和权限投影该配置；详情不产生提交，edit 只提交可写字段，copy 重置唯一键和禁止复制的字段。服务端响应模型、创建模型和 PATCH 模型可能不同，不强行共用一份 payload。

详情由“共享字段信息区 + 业务专用区块”构成。审批票、运行日志、交接回执、版本比较、执行预览、工作流画布继续用专用组件；可以复用字段展示/输入，不伪装成普通编辑属性。归档对象/固定历史版本保持只读，新编辑不修改历史原件。

### 5.2 规则单源与国际化

M02 交付操作级契约映射：path/query/body、方法、字段路径、必填/可空/可写、长度/范围/精度/格式/正则、枚举、错误 code/messageKey/参数。后端规则声明是权威，前端 UI 配置只保留布局、控件、显示与无法从通用契约推出的交互，不再手写一套同含义的数值范围。

现状：当前已提交 OpenAPI 有 275 个路径/398 个 operation，没有 OPTIONS operation，类型生成并不提供运行时字段规则。不能把过去讨论视为已交付。建议按用户原先方向，由资源 OPTIONS 返回按方法或 operationId 区分的表单契约，复用后端现有声明/生成机制；它与 CORS preflight 的职责必须明确区分。若后端选择集中 OpenAPI 文档承载相同信息，必须在 M02 记录最终传输方式，前端规则绑定层不能依赖每次按键请求 OPTIONS。

标准规则可来自 tag/schema；跨字段、权限、唯一性、数据库状态和状态机校验保留后端领域实现。不能把任意 Go 函数转成 JS，也不从服务端下发可执行函数。服务端最终校验永远保留。

- 错误采用稳定 code + 字段路径 + 参数，前端按当前语言翻译；已有安全可展示的服务端消息作为兼容处理。三种语言均验证，不能直接把后端内部错误展示给用户。
- 数值/金额区分展示单位和传输单位，按精度契约转换，不用浮点误差裁剪金额；日期区分 date-only、当地时间和带时区时间戳。
- 正则必须验证 Go/JS 方言兼容，不支持的规则明确列为服务端校验，不能默默当通过。
- PATCH 的未提供、显式 null 和空字符串有不同语义；DELETE 的版本/确认条件属于操作契约，不是通用“删除按钮”。
- 限制输入不等于禁止中间态：负号、小数点、中文输入法、粘贴与日期手输都能正常编辑，blur/submit 再提供完整校验。
- 契约缓存按版本、租户/权限变化失效；服务端字段错误映射回控件，跨字段错误留在表单级。元数据缺失/过期/加载失败不允许宣称“已校验”，展示可恢复状态并按契约决定阻断提交。

## 6. 实施顺序与完成边界

完整工作包见配套清单，每项都有来源、目标、依赖、验收条件和当前状态。执行按依赖顺序，不一次铺开所有页面：

1. **M00–M01：基线与入口。** 固定需求/路由/操作矩阵，登记接口，接入协作壳体和租户边界，原生产路由回归。
2. **M02–M03：共用能力。** 只读/编辑/字段错误/规则绑定、列表布局和行为。真实 API 尚缺的契约必须有明确服务任务，先验证已有 API 的认证通路，不能用 Todo 假装协作任务。
3. **M04–M05：项目与任务试点。** 生产工程里完成项目范围、任务列表/看板/日历、详情/草稿/编辑及独立链接；S 层依赖协作项目/任务真实服务。选一个正常用户和一个受限用户完整走通，验证组件路线后再扩散。
4. **M06–M11：协作主链。** 需求/迭代、计划/目标、工作流、会话、执行、质量与交付。每块能独立查看，但跨模块签收必须等真实依赖齐备。
5. **M12–M18：支撑与治理。** 文件知识、组织/Agent/节点能力、报告绩效、预算审批、运维外接、专业工作包与共享发布；缺口也有编号，不能靠“以后”绕过。
6. **M19–M20：跨端与总验收。** Web/包装壳关系、完整矩阵核对、旧路由回归、真实业务链路、规模/故障测试、分批启用与回滚。

依赖列默认是前置 U 能力/契约，不要求等整包 S/R 都通过。M01 的真实项目选择等 S01，M10 的预算闭环等 S11；允许其 U 先验收，推进 M04/M16 后再完成联合 S 验收，不构成互相等待。

可以先做 U 层，但所有未接服务的入口不得在正常生产配置静默降为 mock。开发/测试模拟与真实传输明确隔离；页面不散布 `if(mock)`，只在已有客户端接入边界提供测试实现，不预建通用 mock 框架。验收时同时检查未配置服务、拒绝授权与真正的成功响应。

### 6.1 每批交付包

每批必须提供：精确变更文件、路由/菜单、字段与业务动作清单、接口与错误契约、三语言文案、权限矩阵、测试用例与执行结果、桌面/手机截图、对应 REQ/场景证据、未完成 S/R 的具体工作包归属及下一步。未验收批次不扩散为全仓替换。

### 6.2 切换与回滚

- 原型继续可运行，不删除 localStorage、不改用户现有 4173 服务；源版本作为设计参照。
- 生产新增入口逐模块启用，使用项目既有菜单/权限机制；不增加没有必要的第二个功能开关平台。
- 已迁移模块后续只维护生产实现，原型只保留参照或必要的规格更正，避免双线追功能。
- U 阶段失败可撤回新增入口/代码；S 阶段写入真实数据后，回滚必须兼容 schema/事件与旧客户端，不把“回退前端”当数据回滚。
- 原型样例数据不自动导入真实租户。用户需要保留的演示数据另列映射/冲突处理，不能默认升级为生产事实。
- 部署是后续明确动作，本轮不发布；上线前提交具体可审查结果及回滚步骤。

## 10. 统一资源框架与页面规范（2026-10-16，先规范后整改）

### 10.1 评审结论与实施门禁

新增业务必须优先套用现有框架，既有 IAM 页面也按同一标准排查。实施顺序固定为：核对框架能力 → 更新规范 → 全量资源/页面/操作盘点 → 修复框架共性缺口 → 按批迁移业务 → 真实接口与浏览器验收。不能先逐页拼实现，再以封装名称相同宣称统一；不能以框架能力不足为由长期绕过框架。

复用 `crud/resource`、`CrudForm`、`CommonTable`、`AutoForm`、`AutoTable` 和现有 API 客户端、后端模块/契约/鉴权机制。先验证这些层的职责与兼容性，缺什么补在已有责任层，不另建平行 CRUD、请求、授权或校验体系。单业务特例优先使用现有自定义字段、操作与映射扩展点；只有确实跨资源复用的能力才进入框架。

### 10.2 每项资源必须闭环

资源盘点必须同时登记 REST 路径与方法、字段契约、列表/详情/创建/编辑/删除入口、接口权限、数据范围、字段可见/可写、业务状态限制以及测试证据。每个操作标注“支持 / 业务明确不支持 / 尚缺”，不能空置。

资源统一建模不等于默认开放所有 CRUD。审计等只读资源、审批等状态命令需显式声明允许的操作与原因；已有能力不能在迁移中消失，不存在的操作也不能由框架默认按钮虚构。权限隐藏是交互投影，后端接口授权与行/字段数据隔离仍为最终边界；列表总数、分页、详情、关联候选和导出必须保持相同授权语义。

后端操作契约是字段限制的权威来源；前端资源描述承载布局、控件、显示、交互及操作绑定，不再维护同义校验。标准规则转换集中在框架，复杂业务判断留在领域层，字段错误采用稳定标识、字段路径及参数并支持三语。无法映射的契约必须明确处理并纳入缺口，不悄悄丢失限制。详情/编辑共用字段声明，但请求模型和响应模型按操作分别映射。

新增与编辑共享字段限制，但不得把 POST 必须携带属性等同于 PATCH 必须携带属性。PATCH 省略表示不修改；已呈现并提交的文本字段若后端规则不允许空字符串，统一表单仍须显示不可留空标记。标记由同一编译规则推导，不在页面另写 required/minLength。验收需分别覆盖省略、清空、纯空白、字符数及字节数边界，并检查不合法输入未发起写请求。

### 10.3 页面类别与滚动责任

- 普通资源列表：统一表格、筛选、排序、分页、加载/空/错误/重试、权限动作；工具栏紧凑，视图切换与主操作在空间允许时同行。
- 资源表单：统一新增/编辑/详情/复制模式、字段错误、提交状态及只读保护；复杂字段通过已有扩展点接入。
- 多栏工作区：导航树、角色选择器、权限矩阵保持相应语义，桌面每栏内容独立滚动；一栏变长不能带走另一栏标题、选择项和操作。不把导航选择器强改成 AutoTable。
- 专业页面：文件管理、认证/恢复、状态机与画布等逐项记录专业交互原因，仍复用适用的字段、权限、错误与布局能力；“特殊页面”不是整页免审。

应用壳明确页面是文档流还是填满剩余高度的工作区；工作区从壳到内容维持可收缩的高度链（包括 min-height/min-width），每个内容面板明确一个主要滚动容器。禁止各页用猜测的 viewport 减固定像素修补高度。表格横向溢出只在表格内容区滚动，sticky 元素与滚动容器一致；边缘提示只在对应方向仍可滚动时出现。

带 Tabs 的桌面工作区，资源标题、主要操作及 Tab 导航处于内容滚动区之外；每个激活的 Tab 面板独立承担内容滚动。不得把包住标题与 Tabs 的整栏设为滚动容器就视作完成。验收须实际滚动后比较标题与 Tab 的可见位置，并切换各 Tab 验证短窗口内容、键盘焦点和末项可达。窄屏仍按已声明的文档流/主从方案验收，不强制照搬桌面固定高度。

窄屏必须明确采用堆叠或主从切换，保证两个区域均可到达，不能照搬桌面窄双栏。键盘焦点、滚动边界、200% 缩放、长翻译及弹窗内部滚动均纳入验收，固定栏不能遮挡字段错误、焦点或操作。

### 10.4 分批整改与验收门禁

先完成生产路由、共享组件、弹窗及子视图的全量清册；静态搜索结果只作候选，不能冒充全面行为审计。按“资源—操作—页面—权限—规则—滚动—证据”建立追踪关系。确认影响范围后，先处理公共壳/组件缺口，再以角色多栏页和一个真实 CRUD 资源验证，最后按清册推广；新旧 IAM/业务使用同一门禁。

每批必须证明：真实 API 成功与失败；未登录/无操作权限/跨数据范围拒绝；字段规则与三语错误；详情不写入；列表筛选分页排序与授权一致；桌面左右独立滚动、横向 sticky、窄屏可达与键盘操作。类型检查、lint、测试和构建不能替代这些浏览器/接口证据。未验证项保留待验，不签收整个框架或全站。

### 10.5 框架职责与资源完成标准

新增业务按现有模块及资源规范接入，不因页面需要重新定义已有 entity/instance 的身份、所有权或权限模型。业务扩展接口必须解释其新增领域职责；有 REST 路由或公共组件不等于已自动获得数据隔离、字段权限和可用页面。

| 层次 | 应复用与承担的责任 | 完成依据 |
| --- | --- | --- |
| 模块与接口 | 既有模块生命周期、Huma 操作声明、respx 响应；模块拥有字段规则及业务状态约束 | 适用的增删改查/领域动作有实际注册、输入输出契约和持久化回读证据 |
| 授权与数据范围 | 既有 authz 注册、资源所有权及数据约束；查询和写入分别执行授权 | 列表、总数、详情、修改、删除、候选及导出逐项验证越权拒绝；隐藏按钮不算授权证据 |
| 表单与列表 | CrudResource/CrudForm/CommonTable 组合 AutoForm/AutoTable；页面仅声明展示与业务绑定 | 新增、编辑、只读详情共享适用字段；契约规则、三语错误、加载失败与滚动行为在真实页面通过 |
| 扩展与例外 | 先用既有扩展点；可复用的机制缺口在其责任层补齐，领域判断留在业务模块 | 缺口有对应修改、兼容验证及受影响调用点清单；例外写明业务依据与替代验收，不悬挂 |

框架补缺以当前已确认需求为边界，遵守单一职责、依赖方向和模块自治；不新增平行框架，不为尚无实际需求的未来业务预建抽象。字段 tag/契约可以表达输入约束，但不能取代数据库唯一性、事务一致性、权限或业务状态机。

清单 §11 的每个资源/操作必须标明「已实现且已验证 / 已实现待验证 / 未实现 / 业务不适用及理由」。不得用“已接入 AutoForm”“接口存在”或“测试全绿”代替整条资源链验收；所有适用项有证据后才签收该资源。
