## Placeholder 明确性

Placeholder 只帮助用户理解空字段期望什么值,不能代替 Label、规则说明或错误反馈。所有 Input、Textarea、SearchField、Select/Combobox Trigger、日期时间、上传和关联选择器遵循以下统一要求:

| 控件/字段 | 合格示例 | 禁止示例 |
|----------|----------|----------|
| 邮箱 | `name@example.com` | `请输入邮箱` |
| 登录密码 | `账号密码` | `请输入密码` |
| 设置新密码 | `8–32 位，至少包含 3 类字符` | `请输入新密码` |
| 金额/价格 | `0.00` | `请输入金额` |
| 日期/时间 | `YYYY-MM-DD` / `HH:mm` | `选择日期` / `选择时间` |
| 关键词搜索 | `订单号或桌号`、`门店名称或编号` | `搜索` / `搜索…` |
| 闭集选择 | `营业状态`、`门店时区` | `请选择…` |
| 原因/备注 | `说明退款原因，1–200 字` | `请输入原因` |

- 已知格式或安全示例优先于重复字段名;无法提供示例时,直接写清对象或选择维度。
- 不得在 placeholder 中臆造 PRD 未确认的长度、枚举、阈值或接口规则。
- 唯一性、可用性、权限、库存和提交错误继续使用字段级反馈,不得写进 placeholder。
- 同一业务字段在 Default、Focus、Error、Disabled、Desktop/Pad/Phone 和所有组件实例中使用同一 placeholder 文案。

## 通用错误提示 key

命名规范 `{端}.validation.{类型}`(`{端}` = sys/ops/mch/pos/kds/cust 等);同一类错误全端同名、文案取自[项目 i18n 词表](i18n.md)(zh-CN / en-US / ms-MY)。

| key 后缀 | 触发 | 示例文案(zh-CN) |
|----------|------|-----------------|
| `.required` | 必填项为空 | 该字段必填 |
| `.email` | 邮箱格式非法 | 邮箱格式不正确 |
| `.phone` | 手机号格式非法 | 手机号格式不正确 |
| `.format` | 通用格式/正则不符 | 格式不正确 |
| `.range` | 数值越界 | 超出允许范围 |
| `.too_long` / `.tooLong` | 超长 | 内容过长 |
| `.url` | 链接格式非法 | 链接格式不正确 |

> `.too_long`(后端 snake)与 `.tooLong`(前端 camel)是同一语义在不同端的既有写法,同端内保持一致即可。占位参数(如 `{seconds}`、`{max}`)原样保留。

## 受限输入的实时规则反馈

规则浮层先按操作意图判定:只用于注册、创建、编辑、设置/重置/修改密码、精确确认等**写入新值**的提交操作。登录、搜索、筛选和只读查看不显示规则浮层。符合写操作前提且同时存在多条限制的用户名、密码、邮箱等输入,聚焦或输入时显示锚定字段的规则浮层。浮层属于非交互上下文说明,不是 Select、Menu 或 Listbox;它不接收焦点、不进入 Tab 顺序,也不挤动表单布局。

### 非写操作:不展示任何格式限制说明

**登录、搜索、筛选、只读查看等不写入新值的场景,除不显示规则浮层外,界面上一律不展示位数、字符集、大小写、正则或格式限制说明。** 该约束覆盖所有常驻可见载体:placeholder、字段 Hint/描述、字数计数、卡片副标题、键盘或掩码区说明、分组标题。理由是用户在这里提交的是**已存在的凭证或查询词**,不是新建值;复述规则既不能改变凭证本身,又会让用户误以为旧凭证必须符合当前规则。

- **仍然保留**:字段标签、可辨识的示例型 placeholder(如员工号 `10086`、邮箱 `name@example.com`)、以及**提交失败后**的字段主错误与统一业务反馈。
- **禁止**:`2~8 位数字`、`4 或 6 位掩码圆点`、`8–32 位且含大小写与数字` 这类把校验规则前置到界面的常驻文案。
- PRD 的「校验规则」表继续保留完整正则与值域——它定义**提交时与服务端**的约束,不是界面提示;PRD 需在该表旁明确标注这一区分。
- 写操作不受本节约束,继续按上文的规则浮层与载体选择执行。

### 规则类型与状态

| 类型 | 定义 | 是否阻断提交 | 示例 |
|------|------|--------------|------|
| 必选 `all-of` | 每一条都必须满足 | 是 | 长度 8–32 |
| 禁止 `none-of` | 任一禁用内容出现即失败 | 是 | 密码不含空格、换行、制表符、全角字符或 Emoji |
| 组合阈值 `K-of-N` | N 个候选条件中至少满足 K 个 | 是 | 大写/小写/数字/特殊字符至少 3 类 |
| 建议 `recommended` | 改善质量但不影响合法性 | 否 | 避免连续重复字符 |

每条规则只有三种展示状态:

- `neutral`:字段为空或尚未开始输入,使用中性图标与说明文字,不得把整列规则预先标红。
- `pass`:当前输入满足该条,显示绿色对勾和规则文字。
- `fail`:当前输入违反该条,显示红色 X 和可执行的修正说明。

状态必须同时使用**图标、文字和语义色**,不得只靠红/绿区分。输入变化时仅更新受影响的规则行;“3/4”表示合法性阈值,不是密码强度评分,本期不显示弱/中/强进度条。

### 触发、定位与提交

| 时机 | 行为 |
|------|------|
| Focus 且值为空 | 打开浮层,全部规则为 `neutral` |
| 输入中 | 保持打开并实时更新本地规则 |
| Blur | 关闭浮层;字段下方可保留一条主错误 |
| 再次 Focus | 按当前值恢复各规则状态 |
| Submit | 任一阻断规则失败则阻止提交、聚焦首个无效字段,字段下显示一条主错误;浮层用于展开具体规则 |

常规表单浮层宽度跟随字段,默认在字段下方 `4px` 处左对齐;动态行或表格单元内的输入窄于 `320px` 时,浮层使用 `320px` 最小可读宽度并按左右可用空间收口。下方空间不足时翻转到上方,任何方向都不得超出 viewport。Desktop 紧凑表单基准字段宽 `500px`,Phone 跟随可用内容宽;浮层作为 overlay 覆盖后续内容,不引发页面 reflow 或布局位移。

### 本地规则与接口结果边界

规则浮层**只展示无需接口即可确定的规则**。前端即时反馈只帮助修正输入,后端仍是最终裁决。

| 校验 | 来源 | 展示位置 | 规则浮层 |
|------|------|----------|----------|
| 必填、长度、字符集、格式、K-of-N、已知账号标识包含关系 | 本地确定性校验,服务端复核 | 规则行;提交时可汇总为字段主错误 | 是 |
| 邮箱/用户名/编号可用性或唯一性 | 服务端接口/提交响应 | 字段下方或字段尾部的 checking/available/error 反馈 | **否** |
| 账号是否存在、权限、库存、配额、风控 | 服务端 | 字段级或页面级业务反馈 | **否** |

邮箱规则浮层只列两条本地规则:**邮箱格式正确**、**最多 254 个字符**。邮箱可用性必须由接口判断;存在专用预检接口时,其结果显示在字段级反馈中且只作即时参考,提交时仍由后端唯一约束最终裁决;没有专用接口时,直接在提交返回的 `409/422` 字段错误中处理。登录与找回密码流程禁止通过预检、错误文案或响应差异泄露邮箱/账号是否存在。

### 受限输入的载体选择

所有受限输入都必须登记规则来源和反馈位置,但不等于每个输入都弹出规则浮层。优先使用最轻且足够解释规则的载体:

| 条件 | 反馈载体 | 示例 |
|------|----------|------|
| 多条本地规则、特殊字符集、组合阈值、范围/精度或精确匹配 | Rule Popover | 设置密码、邮箱、员工号、PIN、编号/SKU、价格、确认文字 |
| 单一必填或长度上限 | Label/Hint/Count + 字段主错误 | 普通名称、备注、搜索关键字 |
| 闭集或可由控件阻止非法值 | Select/Radio/Picker/NumberInput/FileInput 自身约束 | 时区、状态、日期、图片类型 |
| 唯一性、可用性、有效/过期、权限或库存 | 字段级接口状态或提交错误 | 邮箱占用、编号重复、邀请码无效 |
| 登录、搜索、筛选、只读查看 | **无 Rule Popover,且界面不展示任何格式限制说明**;只保留标签、示例型 placeholder 与提交后的字段错误/业务反馈 | 邮箱密码登录、员工号+PIN 登录、列表关键字查询 |
| PRD 未给具体阈值或格式 | 标记合同缺口,暂不生成规则文案 | 未定义上下限的税率、支付超时 |

MCH 当前适用字段按以下口径收敛:

| 字段族 | 本地规则浮层 | 服务端结果(不进浮层) |
|--------|--------------|------------------------|
| 注册/创建/编辑中的邮箱 | 格式正确;最多 254 个字符 | 可用性/唯一性、账号存在性 |
| 设置/重置/修改密码 | 8–32、4 类至少 3 类、可见 ASCII、禁用字符、不得包含已知账号标识 | 风控、历史密码策略(如后续启用) |
| 确认密码 | 与新密码一致 | — |
| 登录邮箱与登录密码 | **均不显示规则浮层**;提交时校验必要格式/非空与 ≤64 | 凭证是否正确、账号存在性、锁定状态 |
| 员工号 | 2–8 位;仅数字 | 租户内唯一 |
| PIN | 4 或 6 位;仅数字 | 账号/PIN 冲突策略 |
| 邮件/图形验证码 | 固定位数与允许字符集 | 正确性、过期、尝试次数 |
| 名称/三语名称 | 对象长度;不含换行、制表符等不可见字符 | 作用域内唯一 |
| 编号/SKU/桌号 | 对象长度;允许字符集 | 作用域内唯一 |
| 金额/价格/排序 | 已定义的范围、整数/精度 | 业务状态、库存或资源冲突 |
| 精确确认文字 | 与要求文字完全一致 | 操作权限、资源当前状态 |
| 邀请码 | 仅在 PRD 明确定义本地格式后展示 | 有效、过期、品牌/角色/门店范围 |

税率和支付超时目前只有“边界/精度校验”要求,尚无确定上下限;在接口合同补齐前不得生成看似确定的规则列表。

找回密码流程分两段处理:输入邮箱并发送验证码属于账号查找/发码请求,不显示规则浮层且不得泄露账号存在性;验证码通过后的“新密码/确认密码”属于设置新值,显示密码与一致性规则。

### 正式设计覆盖

截至 2026-07-31，MOS 正式业务 Screens 共包含 37 个 Rule Popover 状态：SYS 4、OPS 2、MCH HQ 21、MCH Outlet 10。每个 Focus 状态均与其无浮层默认态位于同一业务 Section 并直接相邻；登录、搜索、筛选、只读查看与找回邮箱发码状态未增加浮层。`00 确认稿`已在正式化后清空。

### 无障碍

- Label 使用 `for` 或 `aria-labelledby` 关联输入;字段主错误与规则说明使用稳定 `id` 并通过 `aria-describedby` 关联。
- 输入获得焦点时说明浮层可见;规则状态变化使用 `aria-live="polite"` 汇总宣告,不得在每次按键时重复朗读全部规则。
- 字段主错误使用 `role="alert"` 或等价即时通知;提交失败后焦点移到首个无效字段。
- 所有密码、新密码、确认密码输入框都必须在输入框内部提供独立的明文显示/隐藏按钮；按钮使用小眼睛图标并提供可访问名称,不得与非交互规则浮层混成同一点击目标。
